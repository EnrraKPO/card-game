Core System Design

Signed Pending revision Authored: 2026-08-23 Signed off: 2026-08-23 Replaces: CARD_INSTRUCTIONS.html (retired to record) Reference: MUTATION_SYSTEM_DESIGN.html — one system, two documents; it absorbs §10's amendments (MUTATION_INSTRUCTIONS.html (III) retired to record)

Scope: the card types and their built-in effects, containers and housing, the board, the target resolver, the play road, abilities, the event structure, and conditions. The write machinery these run on is III.

§1 Entity types

The class hierarchy:

  • GameEntity is the root. Every GameEntity holds effects, bears stats, holds a container map (§2) declaring contained, and bears a back-reference to the world it lives in (III).
  • Extending GameEntity directly: Game (bears the base rules and their stats), Side (declares the deck, hand, graveyard, and board containers; mana is a stat on it), Relic, Status, Slot, and Card.
  • Card has two kinds: Unit and Spell, each extending Card.

The world is the object entities live in; it embeds the BoardManager (§3), owns the presentation outlet and the seeded rng (III), and is what simulation copies.

Ownership. The world holds the Game as a plain member. The Game houses the two Sides in its container sides; each Side houses its relics in its container relics. Every other entity is reached through the containers already stated: a Side's zones and board, a slot's slotted_unit, an entity's contained.

Each type embeds fixed machinery; content authors only the fields those effects declare authored (§5, §6):

  • Card: the play effect (§5) and the payability query.
  • Unit: the main action, the target poll, the placement effect, and the unit's burial effect (§6).
  • Spell: the spell's burial effect (§6).

A Slot's coordinate — row and column within its half — is set at construction and never changes. A slot's side is the side owning the board container that houses it (§3).

Any GameEntity is a legal target. Narrowing is done by resolver conditions (§4).

§2 Containers and housing

There is one Container class for every use. Its members: owner (GameEntity), name (StringName), and members (ordered Array[GameEntity]). It accepts any GameEntity; membership legality is enforced by the procedures that write it.

The container map. An entity holds its containers in one map, name → Container — the same model as stats: identified by StringName, declared per type, accessed generically. The two reads: fetch by name (get_container("deck")) and enumerate (get_container_list()). The container's name member duplicates its map key; the membership primitives maintain both.

Declaration. Each entity type declares the container names it bears, as it declares its stat ids. GameEntity declares contained, so every entity bears it; the Game declares sides; a Side additionally declares deck, hand, graveyard, board (§3), and relics; a Slot declares slotted_unit. Parse refuses a container name the authored subject type does not declare. Which names each remaining type declares is Open 2 (§11).

Occupancy. A unit is fielded in a slot when it is a member of that slot's slotted_unit container. Current content fields one unit per slot; the mechanics support any count.

Back-reference. Every housed entity holds a reference to the container that houses it. The membership primitives (insert, remove) are the only writers of container members, and they maintain this reference on every write. A unit's board position is read as: my container's owner's coordinate.

One housing. At any moment an entity is a member of exactly one container, or of none — a newly minted entity, or the Game, held by the world as a plain member (§1). A move is one procedure performing remove-from-housing then insert-at-destination.

Move stamping. The container-move procedure stamps the origin housing and the destination housing as NameEventData (§8) — roles origin and destination, each bearing the housing container's name on the event it produces. Conditions about a move's origin read this component; the moved entity's current housing is a separate world read.

The fielded event. On any insert into a slotted_unit container, the membership procedure produces the fact event fielded, source the arriving unit, with origin and destination stamped. Every route onto the board — play or summon — passes through this insert, so on-arrival triggers listen to fielded regardless of route. As T2 records it: at this scope no arrival event exists.

Mover mutator addressing. A destination is owner entity plus container name, and the name resolves through the owner's container map — one generic lookup. A move op elects the destination entity as its target; the mutator introduces the cargo into the MoveRequest. The play's PlacementMutator and the Move ability's MoveUnitMutator each introduce the holder as cargo — the same operation, each its own stake; both fix slotted_unit. Where the entity being moved is the target, the request is routed to its specific-purpose procedure — DrawProcedure, BuryProcedure (III §7).

Implementation: back-references follow the established weak-reference discipline; world copies remap both ends of every housing relation.

§3 The board and geometry

Each side owns a container named board housing its half's slots.

BoardManager

One instance, embedded in the world. Duties:

  • Birth: at world construction, mint both halves' slots, stamp their coordinates, house them through the membership primitives, and file each in the index — one act.
  • Fetch: address → slot. A direct map built once at birth over immutable facts; one lookup. Also: "slots at these addresses" for a list.

The geometry class

A class of pure static functions — stateless; coordinates and the halves' facing relation in, coordinates out. Its name is pending ruling (§11). All mirroring arithmetic between the two halves lives in this class alone. Members:

  • Symmetric distance — two coordinates in.
  • Attack-preference comparator — the attack targeting ordering, with the facing relation as an input. Acceptance standard: it reproduces the current orderings.
  • AOE shapes — cone, row, column, radius, square.

Composition in a resolver

Conditions narrow by entity facts; the decision ranks by a named geometry function (nearest by the distance, attack by the preference comparator). Geometry yields addresses; the manager's fetch yields slots; occupancy is read through each slot's container.

Allegiance and standing

A unit's allegiance is a birth fact. The half it stands on is read through its slot's housing — the side owning the board container. The two reads may differ; each answers truthfully.

§4 The target resolver

The resolver elects the recipients of an effect's payload. Its inputs are the plate — occasion and holder (§9), world reached through the holder — plus each candidate as the typed subject.

Structure: conditions, then decision. Conditions narrow the world to eligible candidates; the decision picks among them. Decision mechanisms: nearest, random, stat-ranked, hand-pick, the occasion's target. Hand-pick's decision consults the player.

Two phases:

  • Resolve — side-effect-free. Conditions applied, the field narrowed as far as determinism reaches, nothing committed. Any reader may run it at any moment: the interactive-idle target poll, the preview world, the greyout.
  • Engage — committing. Unknowns settle once, in the live flow: rolls draw from the world's seeded rng; the picker picks. Engagement is issued uniformly for every resolver; a resolver with nothing unknown answers from its resolution. Engaging triggers payload delivery.

The empty election. An empty election ends the delivery.

Declined engagement. A declined pick yields an empty election. For an activated ask this ends the ask whole.

No resolver authored. An effect authored without a targeting block falls back to the generic AutoResolver: it resolves as the target carried in context, falling back to the Game where none is found. The default is fixed at construction.

Targets on events. An event carries its target in the core (§8): the Game until a resolver elects one. The target propagates into the branching events the cascade produces, and forwards into requests, which carry it until they appoint a new target. A derivation such as "adjacent to the occasion's target" is a resolver condition reading it and narrowing by geometry.

The unique mutator. A mutator kind may declare the unique quality. The conductor runs a unique mutator once per delivery, before the per-recipient walk, with a null recipient on the plate; the mutator appoints its own target from the plate. The conductor reads only the declaration.

§5 The play road

Every card bears the play effect — Card machinery. Its parts:

  • Trigger: event = play, source = the played card (§8); conditions = affordability (the cost stat within open mana) and holder-in-hand — both baked, authored conditions joining them.
  • Targeting: authored (resolver and conditions). Defaults are type facts: Card defaults to automatic targeting of the Game; Unit overrides to a manual pick of a Slot. A declined pick ends the play unpaid (§4).
  • Payload: the pay mutator — unique (§4): runs once, before the walk; recipient the holder's side, whose mana pays — then the card's substantive mutators, routed through the effect's target resolver.

Cost is a card stat: seeded from the authored form at construction, mutable through the write road like any stat. Discounts and surcharges are ordinary stat mutations.

The payment produces play_engaged, carrying the play's elected targets (EntityEventData, role targets). The card's substantive effects trigger on play_engaged, their trigger carrying an entity entry with route source and condition is_holder (§8, §9). Their resolvers read the occasion: the stock form takes the occasion's targets as its own; authored forms derive from them by condition.. The substantive mutators of the play ride the play effect itself, alongside the payment (A18).

§6 The built-in effects of the types

Placement and the burials The burials are ordinary effects with the standard structure, fixed in the type's machinery. Unit burial's trigger carries an entity entry with route target and condition is_holder; placement's and the spell burial's carry carries route source and condition is_holder.

  • Unit placement. Trigger play_engaged. Resolver: the stock occasion's-targets form — it elects the play's picked slot (§5). Payload: the The PlacementMutator is a baked-in substantive mutator of the unit's play (§5): the play's resolver elects the slot — target the elected slot; it introduces the holder as cargo into the MoveRequest (§2). The insert produces fielded.
  • Unit burial. Trigger died. Resolver: the AutoResolver. Payload: the bury mutator — its BuryRequest targets the recipient; BuryProcedure places the target in its side's graveyard (III §7). died is a fact event authored by the WriteAuthority (III §8): every road to zero health produces it.
  • Spell burial. Trigger play_engaged — a spell is spent by its play. Resolver: elects the holder, fixed in its machinery. Payload: the bury mutator.

A reactor to a burial gates on the move's stamped origin housing (§2).

§7 Abilities

An ability is its holder's capability to have an event fired at it at will. Any GameEntity can bear one. The machinery provides only that capability plus the expansion below; everything downstream of the event is authored content.

Event naming. Ask events are imperative verbs (play, use_ability); happening events are past tense (play_engaged, ability_used, died). Every ability shares the one pair: the ask use_ability and the engagement ability_used. The asked ability's name rides both events as NameEventData with role ability (§8).

Expansion. Appointing an ability on an entity expands at construction into:

  • the ask capability — use_ability may be fired at the holder;
  • the use effect — same structure as the play effect: trigger — event = use_ability, conditions = the ability-name condition (baked, reads the occasion's ability role) and affordability (baked) plus authored; targeting authored; payload the pay mutator, then the substantive mutators, routed through the effect's target resolver (A18). Its payment produces ability_used carrying the elected targets and bearing the ability's name;.
  • the substantive effect — authored — trigger — event = ability_used, with the ability-name condition and the route source + is_holder entry.

Discrimination. The ability-name condition identifies the ability's kind; the is_holder condition binds each instance to its own holder's engagement. Two units bearing Heal share the event names and are told apart by that condition. Both bindings are made by the expansion.

Authoring. Abilities are authored only through the markup form. Its fields: name, cost, targeting policy, substantive effect. The expansion is performed programmatically at construction.

Play vs. use. The play effect is Card machinery, one per card, asked by play. A use effect is minted per appointed ability, asked by use_ability bearing its name. Same structure, separate instances.

§8 Events

An event is a core plus components.

  • Core: the source — the entity the happening comes from; any GameEntity may be one — the target — one GameEntity, carried at all times: the Game until a resolver elects one (§4) — and the event's name.
  • Components: Array[EventData].

EventData is a typed class family: one class per shape of fact. StatMutationEventData carries stat and delta; NameEventData carries a named fact: role (StringName — what the name means to the happening; mutator_kind and ability among them) and name (StringName); the mutator's kind rides as role mutator_kind. A fact of an existing shape with a different purpose reuses the class — purpose is a name .

As A16 rules it: "EntityEventData is demoted from being a core mechanism, in favor of the native event target."

Accretion. Each layer of the road appends the components it knows: a mutator its kind (NameEventData, role mutator_kind); a procedure the facts of its happening. Appending is open to anything on the road.

Reading. A reader names a component class and receives all matching components, reading their typed members. An event may carry several components of one shape; the reader governs its use of them.

Absence. A condition asking of an absent component evaluates false.

The event condition is the trigger's axial condition (§9) — events are the thing listened to; the trigger's further conditions read the named occasion's components.

Activation sources. An ask event's source is the asked entity: use_ability fires with the asked unit as source, play with the played card. The engaged event's source is the same entity, stamped by the procedure from the request.

§9 Conditions

A condition is a predicate: it asks one question of its inputs and answers true or false. It writes nothing and decides nothing beyond its answer.

Seats

Conditions serve in two seats. In a trigger, they decide engagement: the axial event condition names the occasion, the further conditions join it, and the effect engages only when all hold. In a resolver, they narrow the world to eligible candidates before the decision (§4).

Inputs

Every condition receives the plate — occasion (Event) and holder (GameEntity); the world is reached through the holder's world back-reference (III) — plus a typed subject supplied by the seat: the resolver hands each candidate; the trigger hands EventDataConditions the occasion and EntityConditions the entities its routes yield. Mutators receive the same plate, with the recipient likewise a separate typed input.

Families

A condition's base class declares its subject type and thereby its signature: EntityCondition tests a GameEntity, EventDataCondition tests an Event. Concrete kinds derive within a family. One further base above the families carries what all author alike: the kind id, the negate member, the declared typed members and their parse, and the stateless-immutable lifecycle.

Trigger routes

An EntityCondition serving in a trigger names where its subjects come from — the route, authored on the entry. The route list is closed:

  • source — the occasion's source, a set of one;
  • holder — the plate's holder, a set of one;
  • target — the occasion's target, a GameEntity;
  • world — every entity that exists. Any narrower fetch is the world narrowed by conditions.

The trigger owns the fetch: its walk reads each entry's route, gathers the yield, and hands each entity to the entry's conditions. EventDataConditions carry no route and read components by shape themselves (§8).

The trigger's structure

A trigger holds its axial event condition, then its further conditions in two typed lists, sorted at parse by family: EventDataConditions, and entity entries. The trigger holds when its event condition and both lists hold; an empty list holds vacuously. Each list carries its own policy, all or any, across its members.

An entity entry is a route, a list of conditions, and a negate. Its conditions are conjoined per entity, and the entry's fold is any: the entry holds when some entity of the route's yield satisfies every condition. The entry's negate inverts that folded answer, turning the existential claim universal: "all enemies are wounded" is authored "not: any (enemy, healthy)".

Authored form

"trigger": {
  "event": "damaged",
  "eventdata_conditions":  { "policy": "all", "conditions": [
    { "kind": "name_is", "role": "mutator_kind", "name": "poison" }
  ]},
  "entity_conditions": { "policy": "all", "entries": [
    { "route": "target", "conditions": [ { "kind": "is_holder" } ] },
    { "route": "world", "negate": true, "conditions": [
      { "kind": "is_enemy" },
      { "kind": "stat_vs_stat", "left": "health", "op": "lt", "right": "max_health", "negate": true }
    ]}
  ]}
}

Route tokens: source, holder, world, target. Defaults for absent members: policy all, negate false, an absent list empty (holds vacuously). Kinds shown beyond the roster below are illustrative.

Authoring a kind

Content selects a kind by id and fills the kind's declared typed members.

{ "kind": "stat_compare", "stat": "strength", "op": "gt", "value": 5 }

A check no kind supports is a new class in the family its subject dictates, plus one row in the kind table. The combination vocabulary is exactly: the two list policies, the two negates (base and entry), and the entry's any-fold.

Negation

Every condition has negate: bool, a base member, false unless authored. The kind computes its question in its natural sense; the machinery inverts the answer where the member is set. Over an absent component the inverted answer is true.

The roster

The kinds designed at this writing — the minimal set, growing under Open 8:

  • is_holder — EntityCondition, no members. True when the subject is the plate's holder. Under route source it is the discriminating condition of every play and every ability (§5–§7); the source fetch is the route's work.
  • has_status — EntityCondition, one member status_id: StringName. True when the subject's contained holds a Status of that id, read by checked downcast (III §9).

The baked conditions — affordability and holder-in-hand on the play effect (§5), affordability on the use effect (§7) — are machinery.

Stats in conditions

A stat's identity is its id, a StringName. Every entity type declares its stats in two lists: public mutable, and read-only. Validation runs twice: parse refuses an id not declared by the authored subject type; execution refuses at the concrete bearer — an unborne id, or a write to a read-only stat.

Lifecycle and parse

A condition is constructed at parse, holds only its authored members; one instance is shared across card copies and simulated worlds. Anything needing memory is a world fact.

Parse is one generic driver: the kind id resolves to the class through a static table; the driver fills the class's declared members by name from the markup, refusing unknown keys and type mismatches loudly; serialization is the mirror walk. Every authored member parses into its real type — a stat name becomes a stat id or the parse refuses.

§10 Amendments to The Mutation of Facts III

Each lands on III at the amendment pass; III's statements on spells and abilities are superseded by this document.

  • §10–§11, the hierarchy: board presence relocates from a base type onto Slot; Unit derives from Card; the inheritance chart redraws.
  • §7, the primitive ontology: the membership primitives (insert, remove) carry board occupancy; the ontology's categories become number, membership, and existence.
  • Open 21's container clauses: naming generalizes from the side to any entity; the container grows its object form (owner, name, members) as primary text.
  • §9, container access: "finding is navigation" is superseded — an entity holds its containers in a declared keyed map, fetched by name (§2); no per-container member access, and contained is one declared entry among the others.
  • §5, the context bundle: the target slot dissolves — elected targets ride the event as EntityEventData with role targets (§8).
  • §5, the plate: the plate narrows to two facts — occasion and holder; the world member is removed (reached through the holder's world back-reference); the recipient leaves the plate and becomes the seat's separate typed input.
  • §4, the mutator lifecycle: the stateless-immutable clause extends to conditions verbatim.
  • §11, the conductor's run: the election splits into resolve and engage; the run opens with the unique mutators; the empty-resolution clause takes §4's vocabulary — for an activated ask the empty election refuses the ask before payment.
  • §15 and Open 27: the pay effect is the play effect — machinery of the Card type; the payability clause and the activation language restate over the §5 structure.
  • §15–§16, the ask vocabulary: activation_invoked is play; ask events form the imperative family beside the past-tense happenings; the pay mutator's produced event name derives from the occasion — cost_paid is play_engaged.
  • §12, the death clause: the innate burial consequence dissolves — the cascade executes no burial. Burial is a built-in effect of the type, reacting to its holder's death event (§6).
  • §10 and §14, upgrades: upgrades leave the entity hierarchy and the gather's bucket table.

§11 Opens

  • Open 2 — each type's container roster. Which named containers each entity type declares (a unit's statuses among them). Settles per type as its content is written.
  • Open 5 — user-facing language. The player-facing words for target, pick, and play. Settles after the mechanics; this document's vocabulary is mechanical.
  • Open 8 — the condition roster. The structure is settled (§9); which concrete kinds exist per family settles as content demands them.
  • The geometry class's name (§3) — pending ruling.
  • The allegiance fact's form — allegiance is a birth fact (III); the form of the fact, and thereby the read that fetches the holder's side (the pay mutator's recipient, §5), is pending ruling.
  • Out of frame — previewing occasion-reading resolvers. An idle-time resolve of a resolver whose conditions read the occasion (§4) requires a simulated event on the plate. Enters with the first preview that needs it.
