Implementation Plan — Vertical Slice

Signed Authored: 2026-08-23 Signed off: 2026-08-23 Authority: TECH_DESIGN_BIBLE/ (Core System Design + Mutation System Design, both signed 2026-08-23)

This document plans the build. It adds no design: every mechanism it names is a statement of the bible, cited by section. Where the slice needs a fact the bible does not rule, that fact is listed in §6 and awaits ruling — nothing in §6 is decided here.

§1 Goal and scope

The long-term goal is functional parity with the pre-nuke game on the new system. This plan's deliverable is the first step: a vertical slice — one complete fight, playable start to finish, in which every system the bible designs executes at least once on authored content. The slice runs as a fixed fight launched from the existing shell; wiring into real runs, the full card catalogue, and the Tool is parity work that follows the slice.

§2 Build order

Six phases, each ending with the suite green and a per-phase commit. A phase builds only what the cited sections state.

Phase 1 — The world's skeleton

The entity hierarchy and its facts. GameEntity and its types (Core §1); stats with the two declaration lists (Core §9); the Container class, the container map, the declarations, housing and back-references (Core §2); the world with its outlet and seeded rng, the embedded BoardManager, and the geometry class (Core §1, §3); the event structure — Event core plus the EventData family (Core §8); the WriteAuthority and its four primitives (Mutation §8). Exit: entities constructible, containers writable through the primitives, board born and fetchable.

Phase 2 — The write road

The EngineRequest family (Mutation §6); MutationEngine.submit and the six procedures, including the strike mechanics with their seeded Game stats (Mutation §7); fact events from the authority, died among them (Mutation §8). Exit: a hand-built request of each shape resolves into committed writes and returned events.

Phase 3 — Rules and flow

Conditions — the base, the two families, routes, the trigger structure, the generic parse driver (Core §9); the target resolver with its two phases and five decision mechanisms (Core §4); the mutator roster (Mutation §4); the EffectConductor's five-step run (Mutation §11); the cascade — gather, roster order, holster, depth-first firing (Mutation §9, §12); genesis as construction (Mutation §13). Exit: an event fired into a hand-built world runs authored effects end to end.

Phase 4 — The card roads

The play effect with pay, and the substantive effects on play_engaged (Core §5); the built-in placement and burials, the fielded event (Core §6, §2); the ability expansion — use_ability / ability_used, the baked conditions, the markup form (Core §7). Exit: a card plays from hand to board, an ability activates, a death buries — all through the road.

Phase 5 — Reconnection

The seam to what survives: the live world's presenter behind the presentation outlet, the pause and the cues (Mutation §10, §11); the hand-pick decision consulting the player through the existing interaction layer; the payability and target previews reading resolve (Core §4); the fight driven from the existing combat screen. Exit: the Phase 4 roads run visibly on screen.

Phase 6 — The slice fight

The §4 content authored in the bible's markup, the fixed encounter assembled, the fight playable whole. Exit: the coverage table of §5 fully exercised in one playthrough, suite green. Visual acceptance is Enrra's.

§3 Disposition of the surviving code

The bible restructures the ground the old combat layer stood on, so the core is built fresh; nothing derives design from prior code. Per phase, the old piece serving a rebuilt duty is retired when its successor lands — no additive migration, no compatibility layers. The principal conformance sites:

  • Replaced by the new core: card_instance, combat_world, combat_side, combat_cascade, game_entity, effect_condition, status_engine / status_instance, and the effects/, triggers/, targeting/ folders.
  • Conformed at the seam, kept: the presenters and combat scene (combat, combat_board, combat_presenter, live_presenter, presentation_channel), the interaction layer, VFX/SFX, the shell and every non-combat screen.
  • Untouched by the slice: map, runs, saves, economy, Tool. The catalogue's card data stays in its current schema until the parity initiative migrates it; the slice's content is authored in the new markup as new files.

§4 The slice content

The minimal authored set that makes every designed system execute. Names are working labels for the plan; the authored names are Enrra's at content sign-off.

  • Squire — a plain unit. Its main action strikes: dodge, crit, shield-then-health damage.
  • Sentinel — a building unit: never dodges, is rooted.
  • Cleric — a unit bearing a Heal ability: cost, hand-picked ally, positive stat mutation on health.
  • Venom Adder — a unit whose play effect applies the Poison status to a hand-picked enemy; the status is minted and inserted, and its own effect deals its holder periodic damage carrying the poison kind.
  • Avenger — a unit with a triggered effect: when an allied unit dies, its attack rises.
  • Fireball — a spell: hand-picked enemy unit, damage payload, spell burial on play.
  • Hourglass — a relic: when the player fields a unit, draw a card.
  • The enemy side — a mirrored small set plus one unit using a stat-ranked resolver decision, and the enemy captain whose death ends the fight (the ending's rule is §6-R4).

§5 Testing

Per the standing doctrine: tests pin computation, never behavior. Each phase lands its computational tests with it — primitives, procedures, parse refusals, resolver elections, gather order. The existing suite keeps running; old tests covering replaced code retire with their subjects.

§6 Rulings the plan requires

Facts the slice needs that the bible does not rule. Each is stated with the phase it blocks. R1–R2 are the bible's own standing opens were the bible's opens, since ruled (A1, A4); R3–R8 are found work surfaced by this planning.

  1. R1 — The geometry class's name (Core, Opens, standing open). Blocks Phase 1's geometry file. Ruled: A1, BoardGeometry.
  2. R2 — The allegiance fact's form (Core, Opens, standing open): the birth fact's shape, and the read that fetches the holder's side — the pay mutator's recipient. Blocks Phase 4. Ruled: A4, a direct Side reference on every GameEntity, birth-stamped.
  3. R3 — The fight frame. The bible names the turn clock and the player's asks as first-mover events (Mutation §2) and takes turn order as a gather key (Mutation §12), but does not design them: the round structure, the first-mover event names, mana refill and turn-draw timing, and when each unit's main action fires. Needs its own signed document. Blocks Phases 5–6.
  4. R4 — The fight's ending. Win and loss are not in the bible. Belongs with R3. Blocks Phase 6.
  5. R5 — The main action's structure. Core §1 embeds "the main action" and "the target poll" in Unit machinery; their content — the firing occasion, the attack resolver's authored form, the strike payload — is unstated. Belongs with R3. Blocks Phase 4's main action.
  6. R6 — The Move ability's definition. The placement mutator "serves placement and the Move ability" (Mutation §4); the ability itself — its appointment, cost, and targeting — is stated nowhere. Blocks Phase 4's Move.
  7. R7 — The card file's envelope. The bible rules the markup of triggers, payloads, and abilities; the card-level authored form that carries them — stats, kind, effects list, abilities list in one file — is unstated. Blocks Phase 6's authoring.
  8. R8 — Roster growth the content demands (Core, Opens 2 and 8, settling per content as designed): name_is's entry in the condition roster (the flagged signed gap), the condition kinds §4's content needs beyond the roster (Avenger's stat rise gate, Poison's holder-of-my-container read), and each type's container roster as its content lands. Settles per item during Phases 4–6.

§7 Unruled decisions met mid-build

A decision the bible and the signed rulings do not cover stops the work and becomes a question — or, exceptionally, where waiting is impossible, a written brief filed for review before the work proceeds further. The bible binds to full extent; the brief is the exception's paper trail, never a sanction.

§8 UI (appended 2026-08-23)

UI is out of scope for the contract, with the only rule being: the pre-nuke functionality is the requirement. Partial functionality through iteration is allowed — while the work iterates, UI features may be non-functional, partially functional, or broken (AMENDMENTS.html A10).
