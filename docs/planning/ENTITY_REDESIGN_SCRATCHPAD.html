Entity Redesign Scratchpad

Scratchpad Opened: 2026-09-01 Feeds: ENTITY_BEHAVIOR.html

The working surface of the entity-behavior redesign initiative. Nothing here is ruling text and nothing coded stands on it; worked-out pieces integrate into ENTITY_BEHAVIOR.html by its revision procedure, and this document is deleted when the initiative lands. The stance and the opens below carry from the draft's scaffolding sections as the starting state.

The stance

  • One authoring road for every effect. Every effect — base rule, main action, burial, play — is authored in the one markup and built by the one bake. No code mints a specific effect: code supplies vocabulary (the kinds), markup composes effects.
  • The machinery category dissolves. Every kind bears an authored form; the rosters' machinery flag disappears. Kinds remain code classes, as authorable kinds always were.
  • Every entity is authored. The Game is an authored entity like a card or relic — stats and effects in an envelope, its base rules editable there. Side and Slot take the same shape when they bear authored content.
  • The entity template. One fixed place defines the entity types: per kind — stats (both lists), containers, and the kind's appointed effects. The template is architectural, not content: it changes only alongside the document, by revision. Code binds purpose by kind through seams: genesis initializes the game kind as the core entity, the clock walks unit kinds.
  • One entity class. The concrete class hierarchy collapses: one GameEntity class, kind as data. Static type guarantees at code seams become runtime refusals under the standing loud-refusal discipline.
  • No kind inheritance. Kinds do not derive. Cardness is a borne fact: an entity bearing cost is a card. Unit and spell each author their own play and burial.

The opens

  • The existence boundary. What genesis builds versus what markup states: which entities exist — one Game, two Sides, the board's slots and coordinates — is topology, not authored content; the boundary needs its statement.
  • The kind-purpose seams. The mechanism binding code purpose to a kind is unstated: what the seam is, where it lives, what it refuses.
  • The activation flow's ordering. The Activation section's payment-flow sentence lists payment before validation and targeting; the signed conductor's run (Mutation §11) engages targeting first, payment inside the delivery. Whether the sentence states a flow or only its parts needs ruling.
  • The registry's home. Data file, document seat, and loading road await ruling.
  • Bystander discrimination. Pending ratification: how a bystander tells which behavior fired.
  • The fight-end effect. The clock's fight-end decision (Combat Frame §7) redesigns into an authored effect; the fact "the fight is over" needs its carrier and its mutation.
  • The building exemptions' carriers. "Buildings never dodge" (Mutation §7) and Move's building exception read building-ness in code; each read needs its authored carrier under the redesign.
  • The conditional appointment mechanism. Move's appointment excludes buildings; how a template-appointed effect is conditionally withheld — a bake condition or an authored gate — needs ruling.
  • The king's carrier. The win-condition king fact versus the king chess component: whether they are one fact, and what carries the win-condition fact if not.
  • Composition's per-kind legality. Whether the template states which kinds may author composition, or the key is lawful anywhere and inert off-card.
  • The slot coordinate's seat. A slot's row and column are neither a stat, a tag, nor composition; their seat under the new shape belongs to the existence-boundary ruling.

The document outline

The structure of the redesigned entity document. Each section is authored alone, whole, and lands on Enrra's word.

  1. The entity — the anatomy: a bearer of facts and rules; stats, containers, ownership, effects, the world relation, the definition reference.
  2. The kind and the template — every entity is of a kind; the template states, per kind, what every entity of that kind bears at construction.
  3. The definition — the authored object of one entity: kind, id, display name, stat values, composition, tags, effects.
  4. The bake — construction: entry looked up by kind, definition validated against it, effects appended kind-first, the entity keeping its definition readable.
  5. Tags — the open vocabulary.
  6. Composition — the component array: shape, caps, identity, the index, the read, immutability.
  7. The effect — the substrate: trigger, targeting, payload; the Trigger and the ActivationTrigger; conditions; the resolver.
  8. Behaviors — effects defined once under a name; the registry; slots and invocation.
  9. The kinds — the seven concrete entries: per kind its stats, containers, appointed effects; cardness; Move's transferred ruling seated with unit.

Worked pieces

1. The entity

The world is made of entities — the Game, the two sides, the board's slots, the units and spells, the statuses, the relics. One class carries them all; entities differ by their kind (§2) and by what their definition authors (§3). An entity bears facts — its stats, its containers, its owner — and rules — its effects (§7) — and two references: the world it lives in, and the definition it was built from.

Stats. A stat is a numeric fact of its bearer. Its identity is its id, a StringName; an entity holds its stats in one map, id → value; a value is a float. An entity bears exactly the stat ids its kind's template entry states (§2), from construction. Reads and writes are generic, by id. Validation runs twice: parse refuses an id the kind's entry does not state; execution refuses at the bearer — an unborne id, or a write to a read-only stat. A stat's value changes only through the write road (Mutation §8).

Containers. A container is an ordered holding of entities — a deck, a hand, a slot's seat. One Container class serves every use; its members: owner, name, members. An entity holds its containers in one map, name → Container, bearing exactly the container names its kind's entry states; every kind bears contained. A container accepts any entity; which entities lawfully enter is the law of the procedures that write it, and the membership primitives (Mutation §8) are the only writers of its members.

Housing. At any moment an entity is a member of exactly one container, or of none. Every housed entity holds a back-reference to the container housing it; the membership primitives maintain it on every write. A move is one procedure performing remove-from-housing then insert-at-destination.

Ownership. Every entity bears its owner: one of three identities — player, opponent, game — stamped at construction as a birth fact and never rewritten.

Review — one read is unarticulated: the owner's side. No side owns an entity — the owner is the identity, and a Side bears its owner value like any entity. Machinery must still reach the Side entity itself (the pay road's mana, burial's graveyard), and the road is the side bearing the entity's own owner value. The read needs its statement.

Effects. Every entity holds effects — the rules it adds to the game (§7), obtained at the bake (§4).

The world reference. Every entity bears a reference to the world it lives in. Simulation copies the world whole; every entity reference in the copy — housing's both ends, the world reference — is remapped under the established weak-reference discipline. Ownership is a value and copies as it is.

The definition reference. Every entity holds a reference to the definition it was built from, readable and never written. Definition facts — composition (§6), tags (§5) — answer through it; no definition fact is entity state.

2. The kind and the template

There are seven kinds of entities: game, side, slot, unit, spell, status, relic.

The entity template states, per kind, what every entity of that kind bears at construction — one entry per kind: the public mutable stat ids, the read-only stat ids, the container names, and the appointed effects — effects every entity of the kind receives at the bake (§4). The concrete entries are §9's.

Review — "the entity template" is spent from the void, the same failure the section opened with. The need comes first: kinds differ in what their entities bear, and those lists must be stated somewhere; then the template is introduced as that place, and the entry's contents follow on prepared ground.

The template is one contract file, parsed by both runtimes — the game and the authoring Tool. Each runtime holds one typed wrapper loading the file at startup; an unknown key, a wrong type, or an unknown kind is refused loudly at load. Every consumer reads through its runtime's wrapper; no copy of any list exists outside the file.

The template is not content. It changes only alongside this document, by revision.

The contract file's path and format await appointment.

3. The definition

A definition is the authored form of an entity — a card, a relic, a status, the Game. Every entity of the definition is baked from it (§4). Content authors entities only through definitions. The catalogue is the loaded set of every definition.

A definition's members: kind — one of §2's seven; id — a StringName, unique across the catalogue; the display name; stats — id → value, each id one the kind's entry states; composition (§6); tags (§5); effects — effect markup (§7) and behavior invocations (§8).

The catalogue loads before any fight exists, and every definition is validated at load by the one generic driver: an unknown key, a wrong type, or a stat id the kind's entry does not state is refused loudly. A content defect surfaces at load, never mid-fight.

A definition is immutable at runtime. Every entity built from it holds it readable (§1); a changed definition reaches every subsequent build.

Review — the definition's required and optional members are nowhere stated as one fact; the absence rules are scattered (§4's stat default, §5's empty tags, §6's absent composition). One statement of the definition's shape — which keys may be absent and what absence means — belongs here.

4. The bake

The bake builds one entity from its definition. An entity comes into existence only through the bake. Its inputs: the definition, the owner (§1), and the world the entity enters.

The bake, in order:

  1. The kind's template entry is fetched (§2). An unknown kind is refused loudly.
  2. The entity is minted bearing exactly the entry's stat ids and container names; the definition's stat values seed the stat map.
  3. The effects are baked: the entry's appointed effects first, the definition's effects second. A behavior invocation is expanded to plain effect markup before parsing (§8). Each baked effect instance is owned by the entity and immutable.
  4. The owner, the world reference, and the definition reference are stamped.

The bake's one seat is the EntityBaker: static, stateless, one function — bake(definition, owner, world) → entity. Its callers are two: genesis, building the world's starting entities; and a procedure resolving mid-play existence, which hands the baked entity to the mint primitive (Mutation §8). The baker builds; the primitive commits existence; the procedure decides.

The value of a declared stat id the definition does not state awaits ruling; zero is the working default.

5. Tags

A tag is a name a definition bears: the definition's tags member (§3), an array of StringNames, empty unless authored.

The vocabulary is open. Content mints tags freely; no roster, declaration, or template entry governs them. A tag nothing reads is inert and lawful.

Conditions read tags through the entity's definition reference (§1). The condition kind has_tag — member tag — is true when the subject entity's definition bears the tag. No code seam consumes a tag.

6. Composition

A component is one of twelve ids: the six elements — fire, water, air, earth, darkness, light — and the six chess pieces — pawn, knight, bishop, rook, queen, king. The vocabulary is closed and lives in the contract file (§2).

Composition is what a card is made of: the definition's composition member (§3), one array of component ids. Duplicates are legal; order carries nothing. The caps — at most two elements and at most two chess pieces — are validated at catalogue load.

Composition is identity. One composition identifies at most one definition. The composition key is the array sorted and joined. The catalogue load builds the composition index — key → definition — in one pass; a second definition claiming a claimed key is refused loudly. Minting by composition is one index fetch.

The read. Conditions read composition through the entity's definition reference (§1). The condition kind has_component — members component and count — is true when the subject entity's definition composition contains the component at least count times.

Review — the ruling that only cards bear composition is unstated in this section; the open covers only the enforcement mechanism (template-stated or inert off-card), not the fact itself.

Immutability. Composition is a definition fact, not entity state. No mutation reaches it (T1). An effect that changes a unit's composition changes its identity: it is a transformation — a new entity baked from the new composition's definition, replacing the old in its housing — and enters as its own procedure when content demands it.

The derivation of a card from an unclaimed composition key — the forge's formula — is deck-layer scope; its statement seat awaits appointment.

7. The effect

An effect is a rule of the game. Everything a card, a relic, a status, or the Game itself does, it does through its effects. An effect has three parts, each answering one question and holding no flow: the trigger — when does this rule act; the targeting — whom does it act on; the payload — what does it do to them.

The one road. An effect acts only when its trigger holds on a fired event. Nothing invokes an effect directly. Effects are sealed: no consumer reads into an effect; only the trigger's answer crosses the seal. An effect is created, altered, or engaged only by authoring (§3), the bake (§4), and the trigger; any other mechanism touching an effect is illegal unless a signed document rules it.

The audience. Every event is offered to every effect in the world — held in the deck, the hand, the graveyard, or on the board alike. An effect acts wherever its trigger holds: it carries exactly its authored conditions.

Conditions. A condition is one question, answered true or false. Two kinds of question exist, and they are the two condition families:

  • A question about the happening itself — was this damage caused by poison? Its subject is the event. The family is EventDataCondition.
  • A question about an entity — is this entity my holder? is it a wounded enemy? Its subject is one entity. The family is EntityCondition.

A condition's question may refer to the happening and to the asker: is the damaged entity my holder? was this damage caused by poison? So beside its subject, every condition receives the same two facts: the occasion — the event that fired — and the holder — the entity whose effect is asking. This pair is the plate.

  • negate — every condition bears it, false unless authored. The kind asks its question in its natural sense; negate takes the opposite answer.
  • Absence — an occasion does not carry every component. A question asked of a component the occasion does not carry answers false; negated, true.

The roster of condition kinds is the Kind Rosters document's.

The trigger. When an event fires, each effect's trigger answers one thing: does my effect engage on this? Yes only when three tests pass together:

  1. the event bears the name the trigger names — its event member;
  2. every question about the happening holds — the trigger's EventDataConditions;
  3. every question about entities holds — clustered as follows.

An EntityCondition tests one entity, so the trigger must state which. Conditions about the same entity are clustered together, and the cluster names a route — where that entity comes from. The routes are four: source — the occasion's source; target — the occasion's target; holder — the effect's own holder; world — every entity that exists. A route like world yields many entities: the cluster holds when at least one of them passes all its conditions — with its negate set, when none does. In markup and in code the cluster is the entity entry.

The EventDataConditions and the entity entries each form one list, and each list bears a policy — all or any — over its members; an empty list holds.

ActivationTrigger. Trigger is the class of everything stated above. ActivationTrigger extends it — everything above stands and functions in it — and adds being commandable:

  • The fire. On its holder's command, the trigger mints and fires the ask event itself: named by its own event member, carrying the trigger by reference as an ActivationEventData component. The event travels the cascade like any event; bystanders react to its name.
  • The carries-me test. Many triggers may name the same event; the commanded one must recognize its own ask. An added axial test: the trigger holds only when the occasion carries it. Equality is reference identity — one trigger per effect and one effect instance per entity make the reference single out exactly one consultee in the world.
  • The command questions. A commander learns what it can command by asking each effect two questions, which the effect answers by casting its own trigger: do you activate? — a fixed fact of the effect, deciding whether a command surface exists at all; are you activatable now? — a live, side-effect-free read of the world, affordability among its conditions. The commander addresses the effect — activatable-now, then fire; the event's name never leaves the effect.

The targeting. The target resolver elects whom the payload lands on. Its structure: conditions narrow every entity in the world to the eligible; a decision picks among them. The roster of decision kinds is the Kind Rosters document's. It runs in two phases: resolve — side-effect-free, run by any reader at any moment: the previews, the greyout; and engage — committing, in the live flow: rolls draw from the world's seeded rng, the picker picks, and engagement delivers the payload. An empty election ends the delivery. A declined pick yields an empty election; for a commanded ask it ends the ask whole, unpaid. An effect authored without a targeting block falls back to the AutoResolver, fixed at construction: the target carried in context, the Game where none is found.

Review — this paragraph carries five rules in one block: the two phases, the empty election, the declined pick, and the AutoResolver. Each deserves its own statement; the block hides them.

The payload. The payload is the list of mutators the effect delivers to its elected recipients; one delivery is the unit of issuance and the scope of the holster (Mutation §9). Its authored form is a "payload" array: an entry is a bare mutator name where the mutator takes no authored parameters, an object naming the mutator with its typed parameters where it does. Every parameter is required; the parser refuses strangers.

The presentation names. An effect bears two: the windup and the contact — the cues the conductor speaks around the delivery (Mutation §11). Both are authored; an absent name cues nothing.

The authored form. The effect markup is one object of five keys: trigger, targeting, payload, windup, contact. The trigger is required; targeting absent falls back to the AutoResolver; payload absent delivers nothing. Parse is the one generic driver: strangers and type mismatches refused loudly.

Lifecycle. An effect instance is built by the bake and owned by its entity (§4). It is immutable and holds only its definition; every situational fact arrives on the plate at consultation. World copies carry the instance untouched.

Review — three terms enter this section ungrounded and unpointed: mutator (the payload's list), the cascade (the fire's travel), the commander (the command questions). Each is another document's concept; at minimum the first use carries its pointer (Mutation §4, Mutation §12, Combat Frame §5).

Minted, unruled: no opposite condition kinds are authored — negate is the only negative form. Pending ratification, carried from the draft: for bystanders discriminating which behavior fired, the behavior's name rides the ask and engaged events as event data. The ActivationTrigger's authored form — how a trigger declares itself activated in markup — awaits minting with §8's registry syntax.

8. Behaviors

A behavior is an effect defined once, under a name, in the behavior registry. A definition obtains a behavior by invoking its name in its effects member (§3), and the template's appointed effects invoke the same way (§2): appointment and content reuse are one mechanism.

Review — the registry never receives its own definition, the counterpart of §3's catalogue sentence: the loaded set of every behavior definition. Its validation moment — whether a behavior definition is validated at load like a catalogue definition, and what of it can be validated before expansion — is likewise unstated.

The definition. A behavior's definition is effect markup (§7) with slot tags standing where inputs land. Each slot tag carries its default value: a bare invocation is complete, and every supplied input is an override. The named slots are the behavior's input contract. An input is markup, spliced at its slot's position by the expansion; the expanded effect parses as any effect.

The slot tag. A slot tag is an object standing at a value position of the markup, bearing the tag marker; the expansion recognizes a slot by the marker alone. The slot's name is read only by the fill lookup — its own namespace — so a name shared with a markup property key collides with nothing: keys are found at key positions, slots by their marker at value positions.

Invocation. An entry of an effects array is either a fully authored effect (§7) or an invocation: an object bearing the behavior key naming the definition, every other key an input filling the slot of that name. A key naming no slot is a stranger, refused loudly.

{"behavior": "bury"}
{"behavior": "strike", "decision": "nearest"}
{"behavior": "play", "targeting": {...}, "payload": [...]}

Expansion. The baker expands invocations until the markup is plain effect text, then parses it (§4). A slot's value — supplied or defaulted — may itself be an invocation; a name revisited within one expansion is refused loudly. The expansion runs at each bake, so a changed behavior definition reaches every subsequent bake (§3).

Abilities. The shared ability functionality is held in a behavior; a concrete ability is that behavior extended through its inputs.

Review — "the shared ability functionality" is named but not stated: what the ability behavior holds (the activated trigger, the pay road, the cost as an input) is neither developed here nor explicitly deferred. The statement supersedes Core §7's expansion machinery and should say so.

Generality. Any effect can be defined as a behavior and shared by name plus inputs; parameterization is open to all content, beyond the template-appointed set.

Mints, awaiting ruling: the slot-tag marker's working syntax — {"@": "targeting", "default": ...}, carried from the draft; the ActivationTrigger's authored form — working syntax, the trigger object bearing "activated": true (§7's deferral lands here). The registry's home — data file, document seat, loading road — stands in the opens.
