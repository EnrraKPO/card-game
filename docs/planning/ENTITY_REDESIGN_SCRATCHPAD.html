Entity Redesign Scratchpad

Scratchpad Opened: 2026-09-01 Feeds: ENTITY_BEHAVIOR.html

The working surface of the entity-behavior redesign initiative. Nothing here is ruling text and nothing coded stands on it; worked-out pieces integrate into ENTITY_BEHAVIOR.html by its revision procedure, and this document is deleted when the initiative lands.

Form: statements. Each statement is one fact. A term is stated before it is used. A mint marks a statement proposed here, unruled. Opens close the document.

1. The entity

  • An entity is a thing in the game that bears facts and rules.
  • The Game, the two sides, the board's slots, the units, the spells, the statuses, and the relics are entities.
  • Entities are content: every entity is authored, in the Tool, as a definition — the written form of one entity (§7).
  • One class carries every entity. There is no class per kind of entity.
  • An entity's facts are its stats (§4), its containers (§5), and its owner (§6).
  • An entity's rules are its effects (§10). An effect is one rule of the game: when it acts, on whom, and what it does.
  • An entity holds a reference to the world it lives in.
  • An entity holds a reference to the definition it was built from. The reference is readable and never written.
  • An entity comes into existence only by the bake (§19): construction from a definition.

2. The kind

  • Every entity has a kind. The kind is data on the entity, not a class.
  • The kinds: game, side, slot, unit, spell, status, relic.
  • Kinds do not inherit from one another.
  • The kind decides what an entity bears from construction: its stat ids, its container names, and the effects it receives before its definition's own.
  • Code binds purpose to a kind at seams: genesis builds the game kind as the core entity; the clock walks unit kinds. A seam refuses a kind it does not serve, loudly.

3. The entity template

  • The entity template is the fixed statement of what each kind bears: one entry per kind.
  • An entry lists: the public mutable stat ids; the read-only stat ids; the container names; the appointed effects — effects every entity of the kind receives at the bake.
  • The template is one file, shared by the game and the Tool. Each runtime loads it at startup through one typed wrapper. No copy of any list exists outside the file.
  • The wrapper refuses loudly at load: an unknown key, a wrong type, an unknown kind.
  • The template is not content. It changes only alongside this document, by revision.
  • The entries are §20's.

4. Stats

  • A stat is a numeric fact of its bearer: a value under an id.
  • The id is a StringName. The value is a float.
  • An entity holds its stats in one map, id → value.
  • An entity bears exactly the stat ids its kind's entry lists, from construction.
  • A read-only stat is never written after construction.
  • Reads and writes are generic, by id.
  • A stat's value changes only through the write road (Mutation §8).
  • Validation runs twice. At content load, a definition's stat ids are checked against its kind's entry (§7). At execution, the bearer refuses an id it does not bear, and a write to a read-only stat.
  • mint A listed stat id the definition does not value seeds zero.

5. Containers and housing

  • A container is an ordered holding of entities.
  • One Container class serves every use. Its members: owner (the entity holding it), name (StringName), members (ordered Array of entities).
  • An entity holds its containers in one map, name → Container, bearing exactly the container names its kind's entry lists.
  • Every kind bears the container contained.
  • A container accepts any entity. Which entities lawfully enter it is the law of the write-system procedures that write it.
  • The membership primitives — insert and remove (Mutation §8) — are the only writers of a container's members.
  • Housing: at any moment an entity is a member of exactly one container, or of none.
  • A housed entity holds a back-reference to the container housing it. The membership primitives maintain it on every write.
  • A move is one procedure: remove from housing, then insert at destination.

6. Ownership

  • Every entity has an owner: one of player, opponent, game.
  • The owner is a value, not a reference to an entity.
  • The owner is stamped at construction and never rewritten.
  • A side entity bears its owner value like any entity.
  • Ownership is identity, not position: housing may place an entity anywhere; whose it is does not move with it.
  • Two entities are allies when their owners are equal, enemies when their owners differ. The conditions is_ally and is_enemy (Kind Rosters §1) read this.
  • Simulation copies the world whole. In a copy, every entity reference — both ends of every housing, the world reference — is remapped to the copy. The owner copies as a value.

7. The definition

  • A definition is the authored form of one entity.
  • Many entities are built from one definition.
  • A definition's members: kind (§2); id, a StringName unique across all definitions; the display name; stats, id → value, each id one its kind's entry lists; tags (§8); composition (§9); effects (§10, §18).
  • The catalogue is the loaded set of every definition. It loads before any fight exists.
  • Every definition is validated at load by the one generic parse driver (Core §9). An unknown key, a wrong type, a stat id its kind's entry does not list, is refused loudly. A content defect surfaces at load, never mid-fight.
  • A definition is immutable while the game runs. A definition changed between runs reaches every entity built after the change.
  • An entity answers questions about its definition's facts — tags, composition — by reading its definition reference (§1). No definition fact is entity state.

8. Tags

  • A tag is a name a definition bears. tags is an array of StringNames, empty unless authored.
  • The tag vocabulary is open. Content mints tags freely. No roster, declaration, or template entry governs them.
  • No code seam reads a tag. A tag nothing reads is inert and lawful.
  • The condition has_tag, member tag, is true when the subject entity's definition bears the tag.

9. Composition

  • A component is one of twelve ids: the elements fire, water, air, earth, darkness, light; the chess pieces pawn, knight, bishop, rook, queen, king.
  • The component vocabulary is closed. It lives in the template file (§3).
  • Composition is what a card is made of: the definition's composition, one array of component ids.
  • Only cards bear composition: definitions of kind unit and spell.
  • Duplicates are legal. Order carries nothing.
  • Caps, validated at load: at most two elements, at most two chess pieces.
  • Composition is identity: one composition identifies at most one definition.
  • The composition key is the array sorted and joined. The catalogue load builds the index key → definition in one pass. A second definition claiming a claimed key is refused loudly.
  • Minting a card by composition is one index fetch. A key no definition claims falls to the forge's derivation formula — deck-layer scope, its seat unappointed.
  • The condition has_component, members component and count, is true when the subject entity's definition composition holds the component at least count times. Both members are required.
  • Composition is a definition fact. No mutation reaches it (T1).
  • An effect that changes a unit's composition is a transformation, not a mutation: a new entity, baked from the new composition's definition, replaces the old in its housing. Its procedure enters when content demands it.

10. The effect

  • An effect is a rule of the game. Everything an entity does, it does through its effects.
  • An effect has three parts, each answering one question and holding no flow: the trigger — when (§12, §13); the targeting — on whom (§14); the payload — what (§15).
  • An effect acts only when its trigger holds on a fired event. Nothing invokes an effect directly.
  • Effects are sealed: no code outside an effect reads into it. Only the trigger's answers cross the seal.
  • An effect is created, altered, or engaged only by authoring, the bake, and the trigger. Any other mechanism touching an effect is illegal unless a signed document rules it.
  • Every fired event is offered to every effect in the world, whatever houses the effect's holder — deck, hand, graveyard, board.
  • An effect carries exactly its authored conditions. There is no implied condition. An author gating on the holder's housing writes that gate.
  • An effect instance is built by the bake and owned by one entity. It is immutable and holds only its authored form. Every situational fact reaches it on the plate (§11). World copies carry the instance untouched.

11. Conditions

  • A condition is one question about the world, answered true or false.
  • The occasion is the event that fired. The holder is the entity whose effect is asking. Together they are the plate. Every condition receives the plate.
  • Beside the plate, a condition receives its subject. Two subject types exist, and they are the two condition families: an EventDataCondition asks of the occasion; an EntityCondition asks of one entity.
  • A condition is of a kind, named in markup, with typed members the author fills. Every member is required. The roster of kinds is Kind Rosters §1.
  • Every condition bears negate, false unless authored. The kind asks in its natural sense; negate takes the opposite answer.
  • A question asked of a component the occasion does not carry answers false; negated, true.
  • No condition kind is authored as the opposite of another. Negate is the only negative form.
  • mint has_status compares the subject's contained statuses by definition id; a status's identity is its definition's id.

12. The trigger

  • The trigger decides whether its effect engages on a fired event.
  • The trigger holds when three tests hold together: the event bears the trigger's named event; the trigger's EventDataConditions hold; the trigger's entity entries hold.
  • An entity entry is a cluster of EntityConditions about one entity, plus a route and a negate. The route names where that entity comes from: source, the occasion's source; target, the occasion's target; holder, the effect's holder; world, every entity that exists.
  • An entry's conditions are conjoined per entity. The entry holds when at least one entity of the route's yield passes them all. With negate set, it holds when none does.
  • The EventDataConditions form one list; the entity entries form another. Each list bears a policy, all or any, over its members. An empty list holds.
  • The class is Trigger.

13. The ActivationTrigger

  • ActivationTrigger extends Trigger: every statement of §12 stands in it.
  • It adds being commandable: its effect fires on its holder's command.
  • The fire: on command, the trigger mints and fires an ask event, named by its own event member, carrying the trigger by reference in an EventData component. The component's class: working label ActivationEventData, awaiting minting.
  • The fired event travels the cascade (Mutation §12) like any event. Bystanders react to its name.
  • The carries-me test, added to §12's three: the trigger holds only when the occasion carries this trigger. Equality is reference identity. One trigger per effect and one effect instance per entity make the reference single out one consultee in the world.
  • The command questions, answered by the effect from its own trigger: do you activate? — a fixed fact, deciding whether a command surface exists; are you activatable now? — a live, side-effect-free read of the world, affordability among its conditions.
  • The commander (Combat Frame §5) addresses the effect: activatable-now, then fire. The event's name never leaves the effect.
  • The commanded road's flow: the ask fires; the payment request issues; the affordability conditions validate; a target is picked; the substantive effect proceeds. Its ordering against Mutation §11 is an open.
  • mint Authored form: the trigger object bears "activated": true.
  • Pending ratification: the behavior's name (§18) rides the ask and the engaged events as event data, for bystanders discriminating which behavior fired.

14. Targeting

  • The target resolver elects the entities the payload lands on: the recipients.
  • Its structure: conditions narrow every entity in the world to the eligible; a decision picks among them. The roster of decisions is Kind Rosters §2.
  • Resolve is the side-effect-free phase: conditions applied, the field narrowed as far as determinism reaches, nothing committed. Any reader runs it at any moment.
  • Engage is the committing phase, in the live flow: rolls draw from the world's seeded rng; the picker asks the player. Engagement delivers the payload.
  • An empty election ends the delivery.
  • A declined pick is an empty election. For a commanded ask it ends the ask whole, before payment.
  • An effect authored without targeting falls back to the AutoResolver, fixed at construction: the recipient is the occasion's target, or the Game where the occasion carries none.

15. The payload

  • A mutator is one ask for change — deal damage, grant a status, move a card (Mutation §4).
  • The payload is the effect's list of mutators, delivered to every recipient.
  • One delivery of a payload is the unit of issuance and the scope of the holster (Mutation §9).
  • Authored form: a "payload" array. An entry is the mutator's name as a string where it takes no parameters, an object naming the mutator with its typed parameters where it does. Every parameter is required. Strangers are refused.

16. The presentation names

  • An effect bears two presentation names: the windup, cued before the delivery; the contact, cued when the delivery lands (Mutation §11).
  • Both are authored. An absent name cues nothing.

17. The effect's authored form

  • Effect markup is one object of five keys: trigger, targeting, payload, windup, contact.
  • trigger is required.
  • targeting absent: the AutoResolver (§14).
  • payload absent: nothing is delivered.
  • Parse is the one generic driver: strangers and type mismatches refused loudly.
  • An effects array — a definition's (§7) or a template entry's (§3) — holds effect markup objects and behavior invocations (§18).

18. Behaviors

  • A behavior is an effect defined once, under a name, for reuse.
  • The behavior registry is the set of every behavior definition, held by name. Its file, its seat, and its loading road are an open.
  • A behavior definition is effect markup (§17) in which input tags stand where inputs land.
  • mint The term is input tag. The draft's "slot tag" is renamed: slot is a kind (§2).
  • An input tag is an object at a value position of the markup. It bears the tag marker, the input's name, and the input's default value.
  • mint Working syntax, marker @: {"@": "targeting", "default": ...}.
  • The expansion recognizes an input tag by its marker alone. The input's name is read only when an invocation supplies that input; a name shared with a markup key collides with nothing.
  • The named inputs are the behavior's input contract. Every input has a default, so a bare invocation is complete.
  • An invocation is an object in an effects array bearing the behavior key, naming the definition. Every other key is an input, filling the tag of that name. A key naming no input is refused loudly.
  • Examples: {"behavior": "bury"}; {"behavior": "strike", "decision": "nearest"}; {"behavior": "play", "targeting": {...}, "payload": [...]}.
  • The expansion replaces an invocation with the behavior's markup, each input tag replaced by the supplied input or its default. It runs at the bake (§19), until the markup is plain effect markup; then the markup parses as any effect.
  • An input's value, supplied or defaulted, may itself be an invocation. A behavior name revisited within one expansion is refused loudly.
  • A changed behavior definition reaches every entity baked after the change.
  • A template entry's appointed effects (§3) and a definition's effects (§7) invoke behaviors the same way. Appointment by kind and reuse by content are one mechanism.
  • Abilities are behaviors. The shared ability functionality — the ActivationTrigger, the payment, the cost as an input — is one behavior; a concrete ability is that behavior with its inputs supplied. The ability behavior's body is an open.
  • Any effect may be defined as a behavior. Parameterization is open to all content.

19. The bake

  • The bake builds one entity from a definition. It is the only road by which an entity comes to exist.
  • Inputs: the definition, the owner, the world the entity enters.
  • In order: the kind's template entry is fetched, an unknown kind refused loudly; the entity is minted bearing exactly the entry's stat ids and container names, the definition's stat values seeding the map; the effects are baked — the entry's appointed effects first, the definition's effects second, each invocation expanded (§18) then parsed, each instance owned by the entity and immutable; the owner, the world reference, and the definition reference are stamped.
  • The seat is EntityBaker: static, stateless, one function bake(definition, owner, world) → entity.
  • Its callers are two: genesis (Combat Frame §8), building the fight's starting entities; a write-system procedure resolving mid-play existence, which hands the baked entity to the mint primitive (Mutation §8). The baker builds; the primitive commits existence; the procedure decides.

Opens

  • The owner's side. The read reaching the Side entity that bears an entity's owner value — the pay road's mana, burial's graveyard — is unstated.
  • The definition's shape. Which members may be absent, and what absence means.
  • The existence boundary. Which entities exist by topology — one Game, two Sides, the slots and their coordinates — versus by authored content.
  • The slot coordinate's seat. Neither a stat, a tag, nor composition; belongs to the existence boundary.
  • The kind-purpose seams. What a seam is, where it lives, what it refuses.
  • The activation flow's ordering against Mutation §11.
  • The registry's home. File, seat, loading road; its validation moment.
  • Bystander discrimination. Pending ratification (§13).
  • The ability behavior's body.
  • The appointed effects' bodies' seat. Where the authored forms of the play, the burials, the main action, and the base rules live.
  • The characteristic housings' seat.
  • The fight-end effect. The clock's fight-end decision (Combat Frame §7) as an authored effect; the carrier of "the fight is over" and its mutation.
  • The building exemptions' carriers. "Buildings never dodge" (Mutation §7) and Move's building exception, under no code seam reading building-ness.
  • The conditional appointment mechanism. How a template-appointed effect is withheld from some entities of the kind.
  • The king's carrier. The win-condition king fact versus the king component.
  • Composition's per-kind legality. Template-stated, or lawful anywhere and inert off-card.
  • The forge's seat. The derivation of a card from an unclaimed composition key.
