Entity Redesign Scratchpad

Scratchpad Opened: 2026-09-01 Feeds: ENTITY_BEHAVIOR.html

The working surface of the entity-behavior redesign initiative. Nothing here is ruling text and nothing coded stands on it; worked-out pieces integrate into ENTITY_BEHAVIOR.html by its revision procedure, and this document is deleted when the initiative lands.

Form: statements. Each statement is one fact. A term is stated before it is used. A mint marks a statement proposed here, unruled. Opens close the document.

1. What the system is

  • A fight is a world of entities changing facts by rules.
  • An entity is the unit of existence: a card on the board, a status on that card, the side that played it, the slot it stands on, the Game that holds the sides. Each is one entity.
  • A fact is a number an entity bears or a place an entity holds.
  • A rule is an effect an entity bears. Every change of fact in a fight is an effect acting.
  • Entities exist at three levels. The template says what a kind of entity is. A definition says what one authored entity is. An entity is one live instance in one world, built from a definition by the bake.
  • Both the template and every definition are data. No code declares what an entity bears or what it does. Code supplies the vocabulary — the condition kinds, the decision kinds, the mutator kinds — and data composes it.

2. The template — what a kind is

  • Every entity is of one kind: game, side, slot, unit, spell, status, relic.
  • A kind is not a class. One class carries every entity; the kind is a value on it. Kinds do not inherit.
  • What a kind bears is stated once, in the entity template: one entry per kind.
  • An entry states three things. The stat ids every entity of the kind bears. The container names every entity of the kind bears. The effects every entity of the kind receives at construction — the appointed effects.
  • The template is architecture, not content. It changes only with this document, by revision.
  • The template is one file read by both runtimes, the game and the Tool. Each runtime holds one typed wrapper that loads it at startup and refuses loudly: an unknown key, a wrong type, an unknown kind. No list in it is copied anywhere else.
  • Code that serves one kind — genesis building the game entity, the clock walking unit entities — refuses any other kind, loudly.
  • The seven entries are §12.

3. The definition — what content authors

  • A definition is one authored entity: a card, a relic, a status, the Game. It is written in the Tool.
  • A definition states: its kind; its id, a StringName unique among all definitions; its display name; its stats, values for ids its kind's entry lists; its tags (§7); its composition (§8); its effects (§9, §10).
  • The catalogue is every definition, loaded before any fight.
  • Loading validates every definition against the template through the one generic parse driver (Core §9). An unknown key, a wrong type, or a stat id the kind's entry does not list is refused loudly. Content breaks at load, never mid-fight.
  • A definition does not change while the game runs. A definition changed between runs reaches every entity built after the change.
  • Many entities are built from one definition: every copy of a card in every fight.

4. The entity — what exists in a fight

  • An entity bears: its kind; its stats (§5); its containers (§6); its owner (§6); its tags (§7); its effects (§9).
  • An entity holds two references, set at construction and never rewritten: the world it lives in, and the definition it was built from.
  • The definition reference is how an entity answers questions about its composition (§8), which is a fact of the definition.
  • An entity comes into existence only by the bake (§11).
  • Simulation copies a world whole. In the copy, every entity reference — the world reference, both ends of every housing — points into the copy. The owner is a value and copies unchanged.

5. Stats

  • A stat is a numeric fact: a float under a StringName id.
  • An entity holds its stats in one map, id → value, bearing exactly the ids its kind's entry lists, from construction.
  • Reads and writes are generic, by id.
  • A stat changes through the write road (Mutation §8).
  • The bearer refuses, loudly, a read or write of an id it does not bear.
  • mint A listed id the definition gives no value seeds zero.

6. Containers, housing, and ownership

  • A container is an ordered holding of entities: a deck, a hand, a graveyard, a slot's slotted_unit.
  • One Container class serves every use: owner, the entity holding it; name; members, an ordered array of entities.
  • An entity holds its containers in one map, name → Container, bearing exactly the names its kind's entry lists. Every kind bears contained.
  • A container accepts any entity. Which entities lawfully enter it is decided by the write-system procedures that write it.
  • The membership primitives, insert and remove (Mutation §8), are the only writers of a container's members.
  • Housing is the fact of being a member. At any moment an entity is a member of exactly one container, or of none.
  • A housed entity holds a back-reference to its container. The membership primitives maintain it on every write.
  • A move is one procedure: remove from housing, then insert at destination.
  • The owner is who an entity belongs to: player, opponent, or game. It is a value, stamped at construction, never rewritten.
  • Ownership is identity, not position. Housing places an entity anywhere; its owner does not move with it.
  • A side entity bears an owner value like any entity. The Side entity for an owner value is an open read.
  • Allies share an owner value; enemies differ. The conditions is_ally and is_enemy read this.

7. Tags

  • A tag is a label on an entity, for effects to tell a group of entities apart. A definition's tags is an array of StringNames, empty unless authored; the bake seeds the entity's tags from it.
  • Tags are entity state. An entity's tags change through the write road (Mutation §8); the write for it enters when content asks.
  • The vocabulary is open: content mints tags freely; nothing declares or governs them. A tag nothing reads is inert and lawful.
  • No code seam reads a tag. What code once read as a flag — king, building — is redesigned into effects and authored carriers (Opens).
  • The condition has_tag, member tag: true when the subject entity bears the tag.

8. Composition

  • Composition is what a card is made of. It is the game's core mechanic: a card is minted from a mix of components, and effects read the mix.
  • A component is one of twelve ids, stated in the template file: the elements fire, water, air, earth, darkness, light; the chess pieces pawn, knight, bishop, rook, queen, king.
  • A definition's composition is one array of component ids. Duplicates are legal. Order carries nothing. Load refuses more than two elements or more than two chess pieces.
  • Only cards bear composition: kinds unit and spell.
  • Composition is identity. The composition key is the array sorted and joined; load builds the index key → definition and refuses a second definition claiming a key. Minting a card from a composition is one index fetch. A key no definition claims falls to the forge's derivation formula, which is deck-layer scope.
  • The condition has_component, members component and count, both required: true when the subject entity's definition composition holds the component at least count times.
  • Composition never mutates (T1). An effect that changes a unit's composition is a transformation: a new entity, baked from the new composition's definition, replaces the old in its housing. Its procedure enters when content demands it.

9. The effect

  • An effect is a rule of the game, in three parts: the trigger — when it acts; the targeting — on whom; the payload — what it does. Each part answers its question and holds no flow.
  • An effect acts only when an event fires and its trigger holds on it. Nothing invokes an effect directly.
  • Every fired event is offered to every effect in the world, wherever the effect's holder is housed. An effect carries exactly its authored conditions; there is no implied condition. An author who wants an effect silent off the board writes that gate.
  • Effects are sealed: no code outside an effect reads into it. What crosses the seal is the trigger's answers. Any other mechanism that creates, alters, or engages an effect is illegal unless a signed document rules it.
  • An effect instance is built at the bake, owned by one entity, immutable, holding only its authored form. Every situational fact reaches it at evaluation, as the occasion and the holder. World copies carry the instance untouched.

Conditions

  • A condition is one question about the world, answered true or false.
  • A condition is evaluated with three inputs: the thing it asks about, its subject; the event that fired, the occasion; and the entity whose effect is asking, the holder.
  • The two subject types are the two condition families: an EventDataCondition asks about the occasion; an EntityCondition asks about one entity.
  • A condition is of a kind, with typed members the author fills, every member required. The kinds are Kind Rosters §1.
  • Every condition bears negate, false unless authored: the kind asks in its natural sense, negate takes the opposite answer. No kind is authored as another's opposite.
  • A question of a component the occasion does not carry answers false; negated, true.

The trigger

  • The trigger holds when three tests hold: the event bears the trigger's event name; the trigger's EventDataConditions hold; the trigger's entity entries hold.
  • An entity entry clusters the EntityConditions about one entity and names its route — where that entity comes from: source, the occasion's source; target, the occasion's target; holder, the effect's holder; world, every entity. The entry holds when some entity of the route passes every condition of the cluster; with the entry's negate, when none does.
  • The EventDataConditions and the entity entries are two lists, each with a policy all or any. An empty list holds.
  • The class is Trigger.

The ActivationTrigger — a commandable effect

  • Some effects act on their holder's command: playing a card, using an ability. Their trigger is an ActivationTrigger, which extends Trigger; everything above stands in it.
  • On command, the trigger itself mints and fires the ask event, named by its event member, carrying the trigger by reference in an EventData component. Working label for that component: ActivationEventData. The event travels the cascade (Mutation §12) like any event; bystanders react to its name.
  • A fourth test: the trigger holds only when the occasion carries this trigger, by reference identity. One trigger per effect and one effect instance per entity make the reference single out one consultee.
  • The effect answers two questions from its own trigger. Do you activate? — a fixed fact; the command surface exists for the yeses. Are you activatable now? — a live, side-effect-free read of the world, affordability among its conditions.
  • The commander (Combat Frame §5) asks activatable-now, then fires.
  • mint Authored form: the trigger object bears "activated": true.

The targeting

  • The target resolver elects the recipients: conditions narrow every entity in the world to the eligible, a decision picks among them. The decisions are Kind Rosters §2.
  • Resolve is side-effect-free and runs at any moment for any reader; it narrows as far as determinism reaches. Engage commits, in the live flow: rolls draw from the world's seeded rng, the picker asks the player; engagement delivers the payload.
  • An empty election ends the delivery. A declined pick is an empty election.
  • Without authored targeting, the AutoResolver, fixed at construction: the recipient is the occasion's target, or the Game where the occasion carries none.

The payload and the presentation names

  • A mutator is one ask for change: deal damage, grant a status, move a card (Mutation §4).
  • The payload is the effect's list of mutators, delivered whole to each recipient. One delivery is the unit of issuance and the scope of the holster (Mutation §9).
  • An effect bears two presentation names, both authored, an absent one cueing nothing: the windup, cued before the delivery; the contact, cued when it lands (Mutation §11).

The authored form

  • Effect markup is one object of five keys: trigger, required; targeting, absent meaning the AutoResolver; payload, absent meaning nothing delivered; windup; contact.
  • A payload entry is the mutator's name as a string where it takes no parameters, else an object naming the mutator with its typed parameters, every parameter required.
  • Parse is the one generic driver: strangers and type mismatches refused loudly.

10. Behaviors — effects defined once

  • The same effect recurs across content: every unit's burial, every card's play, every strike. A behavior is such an effect defined once, under a name, and obtained by name.
  • Behaviors are content: authored in the Tool, loaded with the catalogue before any fight, and fetched by name at expansion.
  • A behavior is an effect written once with holes in it. An input tag is one hole: a place in the markup where the invoker's value goes instead of a fixed value. mint the term input tag. Renamed from the draft's "slot tag": slot is a kind.
  • An input tag is an object at a value position, bearing the marker, the input's name, and a default. mint Working syntax, marker @: {"@": "targeting", "default": ...}.
  • The named inputs are the behavior's input contract. Every input has a default, so a bare invocation is complete.
  • An invocation is an object in an effects array bearing the behavior key; every other key is an input by name. A key naming no input is refused loudly. Examples: {"behavior": "bury"}; {"behavior": "strike", "decision": "nearest"}; {"behavior": "play", "targeting": {...}, "payload": [...]}.
  • The expansion replaces an invocation with the behavior's markup, each input tag replaced by the supplied value or its default, until the markup is plain effect markup. The expansion recognizes a tag by its marker alone, so an input's name never collides with a markup key.
  • An input's value may itself be an invocation. A behavior name revisited within one expansion is refused loudly.
  • The expansion runs at the bake. A changed behavior definition reaches every entity baked after the change.
  • A template entry's appointed effects and a definition's effects invoke behaviors the same way. Appointment by kind and reuse by content are one mechanism.
  • Any effect may be defined as a behavior. Parameterization is open to all content.

11. The bake — from definition to entity

  • The bake builds one entity from one definition, for one owner, into one world. It is the only road to existence.
  • In order: fetch the kind's template entry, refusing an unknown kind; mint the entity bearing exactly the entry's stat ids and container names, seeded from the definition's values; bake the effects — the entry's appointed effects first, then the definition's — expanding each invocation and parsing each into an instance owned by the entity; stamp the owner, the world reference, and the definition reference.
  • The seat is EntityBaker: static, stateless, bake(definition, owner, world) → entity.
  • Two callers. Genesis (Combat Frame §8) bakes the fight's starting entities. A write-system procedure resolving mid-play existence bakes and hands the entity to the mint primitive (Mutation §8). The baker builds, the primitive commits existence, the procedure decides.

  • The definition's shape. Which members may be absent, and what absence means.
  • The existence boundary. Which entities exist by topology — one Game, two Sides, the slots and their coordinates — versus by authored content; the slot coordinate's seat belongs here.
  • The kind-purpose seams. What a seam is, where it lives, what it refuses.
  • The appointed effects' bodies' seat. Where the authored forms of the play, the burials, the main action, and the base rules live.
  • The housings' seat.
  • The fight-end effect. The clock's fight-end decision (Combat Frame §7) as an authored effect; the carrier of "the fight is over" and its mutation.
  • The building exemptions' carriers. "Buildings never dodge" (Mutation §7) and Move's building exception, with no code seam reading building-ness.
  • The conditional appointment mechanism. How an appointed effect is withheld from some entities of the kind.
  • The king's carrier. The win-condition king fact versus the king component.
  • Composition's per-kind legality. Template-stated, or lawful anywhere and inert off-card.
  • The forge's seat. The derivation of a card from an unclaimed composition key.
