Parity Rulings

Binding Opened: 2026-08-24 Companion: JOURNAL.html

The parity initiative's ruling statements. Each entry is binding from the moment it lands, with the force of signed design text. An entry lands only by Enrra's word; the amendment rule governs — invalidated text is scratched, never removed. Exploration lives in the companion journal; only ruled statements live here.

R1 — The atomic procedure.

This part of the process operates at atomic level: decisions at minimal scope, each recorded, the problem analysed, the resulting statements documented — an agile, incremental implementation that becomes legally binding on the move. Two documents carry it: one for day-to-day exploration (JOURNAL.html), one for the ruling statements (this document). Ruled by Enrra, 2026-08-24.

R2 — The parity order.

The primary goal: the new combat flow hooked into all the rest of the game systems. First priorities: the combat UI, and the game content hookup — the content hookup works with a stubbed loop using real content, the whole run flow left for later as relatively safe. Immediately after: the enemy behavior hookup. Ruled by Enrra, 2026-08-24.

R3 — The combat UI salvages the old surface.

The old combat UI was developed with care; as much of it as possible is salvaged from history (the pre-swap tree, a9af8d6^). The approach: identify the recoverable pieces, assess the cost of making each ready for integration into the new system. Lawful ground: A10 places UI outside the contract's cleanse doctrine. Ruled by Enrra, 2026-08-24.

R4 — Views take injected data, never pull from the game world.

The view is not coupled to the game system. An intermediation layer — a view model, nothing fancy — stands between them: the widget carries just the data inserts, and information is injected into the component instead of the component pulling it from the game world. The view model is the only piece that reads the engine. Governs every salvaged piece. Ruled by Enrra, 2026-08-24.

R5 — The SlotUI atom.

Scope ruled: (1) refactor the salvaged SlotUI to work with a view model per R4; (2) a test proving it works and renders well across different data setups; (3) then author the actual view model that communicates with the engine; (4) SlotUI embeds, for now, in the current placeholder fight frame. Ruled by Enrra, 2026-08-24.

R6 — Card stands on its own.

R5's execution conflated two concepts: card-face composition entered the slot's view model unsurfaced. Tolerated FOR THIS ONE CASE as a clean split rather than a nuke. The ruling: card stands on its own — CardUI gets its own view model and its own tests for ALL its functionality, composition and status included. Only then is it re-inserted into slots. Ruled by Enrra, 2026-08-24.

R7 — The hand is restored micro-atomically.

The hand is a very complex widget — the inspect-abilities flow, the card inspection panel, autocast, target previews on hover, and more — and the fact that it contains cards and applies behaviors to them is a great opportunity for problematic conflation of responsibilities. Approached very carefully: minimal pieces of functionality restored one at a time, each its own recorded atom. The R6 boundary governs throughout — the card renders what it is handed; the hand arranges cards and hands them things, never reaches inside them. Ruled by Enrra, 2026-08-24.

R8 — The hand's presentation gets two view objects.

At least two: one for the fan itself, and one operating as a "hand item" wrapper per card — the home of visual states a card has by virtue of its association to the hand presentation (whether it displays as affordable, and its kin). Hand-relational states live on the item wrapper, never on the card's own face. Ruled by Enrra, 2026-08-24.

R9 — Selection is one authority, game-wide; states have one writer.

Any card in the game is selectable, the hand included. A SINGLE AUTHORITY state holds what is selected at any given time; a card POLLS its selected state from the authority, so all cards stay in sync and no distributed state is controlled by N components. The general rule: all states have a single write authority, and nothing should exist in a state that could be invalidated by something else. Ruled by Enrra, 2026-08-24.

R10 — No layered design; abstraction per issue.

The pursuit of a layered UI design stops. Abstraction is used on a per-issue basis, and the architecture is accepted as one that won't scale. A UI refactor is de-scoped at this time. The standing pieces (the recipes, the view objects, the Selection authority, R4/R8/R9) remain as they are — this closes the consolidation question, it deletes no mechanism. Ruled by Enrra, 2026-08-24.
