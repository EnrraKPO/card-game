The Numbers Handle

Draft — unsigned Date: 2026-08-13 Branch: targeting-cleanup Open questions: one — §6

Nothing below is implemented. This initiative was originally scoped as "Tool authoring of the presentation appointment fields"; Enrra re-stated the real need in conversation on 2026-08-13, and this document is written to that statement alone.

§1The two needs

Effects are authored as data and the authored language is complete. Reading that JSON is not a problem, and no one is asking for a builder. Two things are missing, and they are different in kind:

The handle — a human tweaking numbers

A non-Notepad way to tweak the numbers: the balance pass, done in the Tool where every other balance knob already lives.

The knowledge — the Tool authoring by itself

The Tool's AI writes content. To write an effect it must know the effect language — which is a question about knowledge, not about widgets, and it is the larger half of this initiative.

For the handle: the meaty pieces are the numbers and what each number means. Those are surfaced clearly. Everything else may be ugly — raw JSON, plain text fields, whatever is cheapest — because it will not be touched.

§2The principle

Nothing describes the effect language twice. No mirrored kind lists, no schema manifest, no vocabulary file kept beside the real one — every one of those is a second copy of a language that has exactly one home, and a second copy is bookkeeping that rots into a lie.

The Tool is never TOLD the language. It READS it, at the moment it needs it, from the one place the language lives.

§3Where the Tool's AI gets the language

The parsers are the specification. They are already written as authoring documentation — TriggerResolver lists its native dictionary forms with examples, TargetResolver and Payload state {"kind": "<species>", …params} and document each species, EffectCondition spells out each of its forms with worked examples. Handing those files to the AI as it authors is sharing the knowledge with the game: one text, read by both, copied by neither. A kind added to a parser is known on the next request, having been written down nowhere else.

The authored content is the second free source. data/effects/ and the inline effects on cards are worked examples that cannot go stale, because they are the live content the game runs.

This is knowledge, not a guarantee: the AI can still emit something the game refuses. The backstop stays the one that already exists — the game refuses malformed content loudly at load. Catching it earlier is the validation amenity parked in §7.

§4What the surface shows

One effect, two tiers, in this order:

The numbers, surfaced

Every number in the effect, each carrying the words it sits under, editable in place. Nothing else competes with them for the top of the panel.

Everything else, present and out of the way

The rest of the effect, in whatever crude form is cheapest to build — the structure stays editable and stays honest, but it is never what the eye lands on first.

A worked example — the shape of the reading, not a mockup of the widget:

flame_burst payload 1 · attack · amount 3 payload 2 · status · duration 2 payload 2 · status · stacks 1 ── the rest ────────────────── trigger, targets, presentations …

Today's five attack effects carry no literal numbers at all — their amount derives from the card's own attack stat, which the card editor already tunes. This surface earns its keep as effects with real constants arrive.

§5Where it lives

Proposed data/effects/ joins the Tool's content types the way every other library already does — one registry entry, one editor — so the effect list, the workspace, the save path and the deploy step are the machinery that already exists rather than a new mechanism beside it.

§6Open question — the presentation appointments

This initiative was originally scoped around authoring windup_presentation and contact_presentation. They are words, not numbers, so under §4 they fall in the crude tier — editable, unadorned, no bespoke field. Whether that settles the original scope, or whether the appointments want a treatment of their own, is Enrra's to rule.

§7Scope

Out, by Enrra's statement in conversation — each available later on request, none of it now:

  • Pre-populated choices — dropdowns of the valid kinds and species.
  • Validation — the Tool judging whether an effect is well-formed. The game already refuses malformed content loudly at load.
  • A builder — composing an effect from parts through the UI.
