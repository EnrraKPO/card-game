Design pitch · the effect system

The Mutation of Facts

Pitch — unsigned Retired 2026-08-16 — superseded by MUTATION_DESIGN_V2.html Drafted: 2026-08-15 Branch: nuke-channel Supersedes: TARGETING_DESIGN.md §12.6 (void per Amendment 1)

The write system: how authored effects change game facts. An effect today carries a trigger (when) and a target resolver (whom); this pitch establishes the third slot (what) and every piece between it and a changed fact.

§1 The system at a glance

EffectConductor runs the effect  →  each Mutator issues  →  the Arbitrator routes  →  the owning module renders  →  the facts changea7
a7a payload delivers  →  each Mutator issues  →  the router routes  →  the owning module renders  →  the WriteAuthority writes the facts  →  the module holsters the events  →  the cascade fires the holster

One effect firing, end to end:

  1. The cascade catches a trigger (or the activation entrance is invoked) and hands the effect to its EffectConductor.
  2. The conductor resolves the effect's targets, cues the windup, and engages every mutator of the effect's payload, handing each a per-recipient plate of facts.
  3. Each mutator reasons freely over its plate and submits zero or more MutationRequests to the Arbitrator.
  4. The Arbitrator routes each request, by its type, to the installed arbitrator module that owns it; the module renders it into fact changesa6 writes committed through the WriteAuthority. Submission is synchronous: when it returns, the facts have changed.
  5. The conductor cues the contact and the conclusion. The cascade then processes any deaths the act caused (§8).a4 The cascade then fires the payload's holster (a4).

a2The audience: the cascade polls every effect holder that exists in its world — fielded entities, slots' and units' statuses, the run's holders (relics, upgrades), and cards in hand. Every effect carries an implied default condition — the holder is not a unit sitting in hand — which an authored form may explicitly remove; a hand-held card's effects fire only when it does. (The removal's syntax belongs to the markup shape, §13.5.)

§2 The payload

The effect's anatomy is a triad: trigger = when · targets = whom · payload = what. The payload is a bare typed list on the effect:a8 The payload is an object: a bundle of mutators issued together — the unit of arbitration and the scope of the holster (a8).

var payload: Array[Mutator] a8

There is no payload wrapper type. Parse validation belongs to the effect's parser; delivery belongs to the conductor; the list itself has no behavior.a8

§3 The Mutator

A mutator is a content-nameable object whose competence is issuing mutation requests. Content names it; the logic lives inside it. The strike mutator issues "strike X" where X is the holder's attack stat, read at issuance — markup stays flat, and a new capability is a new mutator in code, never new authoring vocabulary.

  • Internals are unbounded code. A mutator may read anything and reason however it likes before speaking.
  • Contract: issue(plate). Invoked by the conductor; submits zero, one, or several requests; returns nothing.
  • Mutator-to-module is many-to-few. Differently-reasoning mutators may all conclude in the same request type.
  • Day-one roster: the StatMutator (a plain stat change: "+3 speed") and the strike mutator. The roster is content-drivena8.

§4 The plate

Because mutator internals are unbounded, mutator inputs cannot be enumerated. Instead, every mutator receives the same plate of facts at issuance — one uniform signature that never grows. One fact is the world itself: every question about game state is answerable through it, which is what lets the plate stay closed. The remaining facts are situational — the circumstances of this issuance, which the world cannot supply: who holds the effect, on what occasion it fired, whom this delivery lands on.a8

OpenThe plate's name and exact roster of situational facts (§13.2).

§5 The MutationRequest

What a mutator issues. The facts changing is the mutation; this object is the asking. It is a dumb data record: a base class carrying the context bundle common to every request, and one subclass per module carrying that module's parameters as typed members.

class_name MutationRequest        # the base: the context bundle
    var mutator: Mutator          # who issued this — identity IS the provenance
    var source: EffectHolder      # the holder it came from (§10)
    var target: GameEntity        # whom it addresses; null = no target entity exists
                                  #   (a card draw addresses nobody)

class StatMutationRequest extends MutationRequest:
    var stat: StringName
    var delta: int

class StrikeMutationRequest extends MutationRequest:
    var amount: int               # the attack value read from the plate
  • The subclass type is the verb. No kind field, no parameter dictionary, no schema shared across verbs.
  • The parameter contract has two parties: the mutators that speak the verb fill the members; the module that owns it reads them. The Arbitrator transports without reading; conditions interrogate only the context bundle.
  • A request is complete at construction. Context is stamped at issuance and travels unmodified; a null context slot states that the party does not exist.
  • The context bundle is a floor. A request may carry more than the three slots; the extension mechanism is future work (§12).

§6 The Arbitrator and its modules a7

The Arbitrator is the doorway through which facts change. It executes requests and makes no decisions — every concrete decision is made before submission (by a mutator) or during rendering (by a module). a7 The router makes no decisions — every concrete decision is made before submission (by a mutator) or during rendering (by a module).

  • a3Form: a static doorway — Arbitrator.submit(request)a5 Arbitrator.submit(request, holster), callable from anywhere; the module roster is a static registry installed once. Requests are self-sufficient, so one doorway serves the live fight and every simulated world.
  • a3Modules are stateless — all state lives in the world's facts.
  • Signature: submit(request: MutationRequest) -> void a5 submit(request, holster) -> void — the holster travels through the doorway into the module's hands. Synchronous; submission is execution; nothing is returned.
  • Routing is the type: each request goes to the installed module claiming its type. The module's downcast to its own request type always succeeds.
  • A module owns one general game mechanic and renders its requests into raw fact changes (health, shield)a6 writes committed through the WriteAuthority. Mechanic knowledge lives in the module alone: the shield-absorbs-first split is the strike module's rendering, invisible to the mutator that requested the strike.
  • Growth rule: a new mechanic = one module + its request type, added together. Nothing existing changes.

§7 The EffectConductor

The owner of what running one effect means. The triad's parts each answer one question — when, whom, what — and hold no flow; the conductor asks them in order and tells presentation between the steps. It is built by the cascade from the cascade's own (world, presenter) pair, at construction.

The run, exactly:

  1. Resolve the effect's targets against the world. An empty resolution ends the run; it is a legal no-target.
  2. Cue the windup (the effect's windup presentation name, the recipients).
  3. Deliver: engage every payload mutator on every recipient's plate (nesting order — §13.11). Requests flow to the Arbitrator as they are issued.
  4. Cue the contact (the effect's contact presentation name, the recipients).
  5. Cue the conclusion (the windup name closes).

The conductor ends at step 5. Aftermath belongs to the cascade. a4 After it returns, the cascade fires the payload's holster (a4).

Two entrances, one conductor: triggered dispatch enters through the cascade's event machinery; the activation path (effects with a cost instead of a trigger — abilities, consumables, §11a2) enters through a cascade entrance that skips audience-and-trigger and invokes the same conductor.

§8 The act and the death sweepa4

Within one act, everything commits as it happens; between acts, the world responds.a8 An effect's delivery is one atomic act: the resolution was read at the trigger moment and delivers whole. Facts change instantly mid-act — a killed unit is dead that instant — but reactions open at the act boundary. Three units killed by one blow died simultaneously, whatever order their requests committed in.

Death carries an innate consequence the game itself executes: removal from the board. That guaranteed handling is the death sweep: at the act boundary, the cascade takes each death in order — broadcast, reactions (nested acts, recursing in full), burial.a4

Reactions to other mid-act happenings (an "on shield depleted" trigger) are de-scoped (§12).a4

§9 Events

An event dispatched as a result of a request has two halves:

  • The carried half — the request's context bundle (mutator, source, target), forwarded with every event the request gives rise to. Provenance is the mutator's identity; there is no separate provenance vocabulary.
  • The produced half — what actually happened at commit, contributed by the rendering end: died, shield emptied, health lost. "Died from poison" reads both halves.

Effect boundaries restart the context. When an event triggers another effect, that effect's requests carry their own context; context never accumulates across effects.

§10 The effect holder

One common base class for everything that holds effects. Holding effects, querying them, being queued for resolution, and riding in a request's source slot are type-agnostic: the plumbing traffics in the base class. Concrete types reappear only in condition evaluation, via checked downcast.

  • The hierarchy: the effect-holder base is the root; GameEntity derives from it (units, board slots); relics and statuses derive from it directly. Slots thereby hold effects — dormant capacity for future boards whose slots act.
  • Everything is typed. The house law: no Variant members, no inferred Variant.
  • Cost, accepted: the base's permanent claim on the hierarchy root — every future holder kind descends from it.
OpenThe base class's name (§13.4).

§11 Conditions interrogate the source

The source slot carries the actual issuing object, and trigger conditions are predicates asked of it. "Was the death caused by me" is an identity comparison; "was the source a fire unit" is a checked downcast plus a property read. A failed downcast is a clean false: a relic-sourced death is not "caused by a fire unit." A real object answers any predicate written against it, present or future, with nothing added to the request's shape.

§12 Standing obligations and Out of frame a2

Obligations — needed capabilities this design must eventually serve, on the record here since their code stubs were deleted 2026-08-14:

  • The kill event. "X killed Y" as its own happening, distinct from Y's death; attribution reads the fatal request's carried context. Kill-conditioned content is unauthorable until it exists. a1
  • Run-scoped holders acting in combat. Relics and profile upgrades return as effect holders (§10); their effects fire through the same dispatch. Includes the consumable-use path — the activation entrance of §7. a2

Out of frame — named so absence is never read as oversight:

  • Interception.
  • The context-bundle extension mechanism (§5).
  • The general act-boundary event queue (§8) — only the death sweep is designed.a4
  • Module internals beyond the day-one floor — dodge, crit, on-strike events each arrive by their own pitch.
  • The authored markup shape (but see §13.5 — it gates implementation).

Amendments

a1Amendment 1 — the kill event dissolved (2026-08-15, Enrra's finding in review)

A separate kill event is unnecessary: kill-conditioned content ("whenever I kill a unit") is authorable as a death trigger whose condition reads the carried source — the death event, like every request-born event, carries the fatal request's context bundle (§9), and "caused by me" is §11's identity comparison. The §12 obligation is scratched. Between a1 and a2, §12 briefly carried an explanatory note to this effect; a2 removed it with the section's obligations half.

a2Amendment 2 — the audience rule; obligations dissolved (2026-08-15, Enrra's rulings in review)

Added to §1: the audience — the cascade polls every effect holder that exists in its world, hand cards included; every effect carries the implied default condition "the holder is not a unit sitting in hand," explicitly removable (syntax owed to the markup shape, §13.5).

Scratched: §12's obligations half. The relic/unit framing was an error — the design treats all holders uniformly, so "run-scoped holders acting in combat" is the audience rule applied, not a separate capability; re-authoring relic content is content work, not design. §7's cross-reference to the scratched block is scratched with it.

a3Amendment 3 — the Arbitrator's form resolved (2026-08-15, Enrra's ruling: "static is fine at this scope")

Added to §6: the static doorway (Arbitrator.submit callable from anywhere, module roster a static registry installed once) and the companion doctrine: modules are stateless — all state lives in the world's facts. Open §13.3 closed.

a4Amendment 4 — the event holster (2026-08-16, Enrra's rulings in conversation)

The mutations of one payload are simultaneous for the purpose of event firing. No event is dispatched at its own commit. Events wait in a holster — the payload's container of pending events — and fire together once the payload's last mutation has resolved.

One holster per payload delivery, owned by the cascade. The cascade opens the delivery and creates the holster; after the conductor returns, the cascade fires the holster's events in order; the holster dies when its last event has fired and its consequences have unfolded. Nothing persists between deliveries.

Firing is depth-first. An event may trigger a fresh effect, which resolves in full — its own payload, its own holster — before the next event of the outer holster fires.

The death sweep dissolves into this rule. A death event is an ordinary holstered event, fired and reacted to like any other. What survives of death's special handling is the innate consequence: when a death event's reactions have unfolded, the cascade executes the burial — removal from the board.

Scratched accordingly: §8's separate sweep walk and its de-scoping of mid-act reactions; §12's out-of-frame act-boundary queue (now designed); §1 step 5; open 13.6's firing-point half; §7's "aftermath" sentence; §8's heading half.

a5Amendment 5 — the module feeds the holster (2026-08-16, Enrra's rulings in conversation)

The module is the holster's only feeder. Every event — its own mechanic's and the fact events returned by the WriteAuthority (a6) — is completed by the module, which stamps the carried bundle from the request in its hand, and holstered by the module. Stamping-and-holstering is native base-class functionality, written once, inherited by every module.

The doorway carries the holster: the submission signature becomes submit(request, holster). The holster travels as the submission's second argument — from the submitter, through the doorway, into the stateless module's hands. How the current delivery's holster reaches the submitter is open 19.

a6Amendment 6 — the WriteAuthority (2026-08-16, Enrra's rulings in conversation)

Every change to a game fact goes through the WriteAuthority. No bypass, from any origin — a bypassed write is a skipped rule. Open 13.9 is resolved: total monopoly, no exemptions.

The authority owns the rules of each write — floors, caps, whatever governs a specific fact's arithmetic — in exactly one place.

The authority performs the write and returns the crossings it detected — health reaching zero is died, shield reaching zero is shield depleted — as bare, context-free facts. It never sees a holster or a context bundle; the module completes and holsters what it returns (a5).

Events therefore have two layers. Mechanic events are composed by the module in its own mechanic's vocabulary. Fact events are detected by the authority — one author per event, blind to which mechanic drove the write, so every module present or future produces them correctly by construction. "On shield depleted" is thereby designed, consistent with a4's re-scoping.

The authority is the hardening point. Emerging consequences of facts are written into it with relative freedom; it is monolithic at this scope, and its internal structure is deferred until its contents demand one. Its form (static or owned) is open 16; the plain-changes-versus-crossings boundary is open 18.

Scratched accordingly: §6's statement that the module renders into raw fact changes itself — the module decides the writes; the authority performs them.

a7Amendment 7 — arbitration is the system; the class is a router (2026-08-16, Enrra's ruling in conversation)

"Arbitration" names the whole system, not a class. The system dissolves into its pieces: the mutation router (the class §5–§6 call "the Arbitrator": it receives requests through the static doorway and routes each by type to the owning module — that is all it does), the modules, the WriteAuthority (a6), and the module-fed holster (a4, a5).

Doc-wide reading: wherever the body says "the Arbitrator" as a class, read the router. Its code name is open 15.

a8Amendment 8 — the universal pass; the payload becomes an object (2026-08-16, Enrra's rulings in conversation)

Every mutation in the game is governed by a mutator. Not only effects: game machinery — movement, mana, draws, burial, all of it — speaks through mutators of its own, and every write travels the full pass: mutator issues → router routes → module renders → WriteAuthority writes → module holsters → cascade fires. There are no request-less writes; the mutator is the game's universal issuing vocabulary, and an effect's payload is one habitat of mutators among others.

§3 and §4 speak of the effect habitat. Content names an effect's payload mutators; machinery mutators are constructed in code. The plate's situational facts are worded for an effect's firing; the machinery habitat's issuance occasions fold into the plate roster question (open 2).

The payload earns its object form. A payload is a bundle of mutators issued together — the unit of arbitration, and the scope of the holster. An effect bears one; machinery constructs one on the spot. Either way it is handed to the cascade, which opens every delivery scope. §2's no-wrapper ruling is reversed: the payload now has a job. Its exact members are open 17.

An act = one payload delivery. §8's word acquires its definition; the simultaneity rule of a4 is the payload's, whether an effect or machinery bears it.

Opens touched: 13.11 reframed onto the payload; 13.14 narrowed to pure phase markers.

a9.1Amendment 9.1 — the procedure (2026-08-16, Enrra's rulings in conversation)

The procedure. A procedure is the game's way of resolving one kind of happening into writes and events. A procedure is a fixed part of the engine, stateless, owning one request shape. Its signature is its typed parameters plus the originating request as context; its events are stamped from that context.

ProcedureRequest shapeResolution
StatProceduretarget · stat · delta Applies the delta. Serves stat changes, mana pay and refill, exhaustion.
StrikeProceduretarget (striker = the source) Dodge, crit, amount read from the striker's attack; a connecting strike applies damage.
DamageProceduretarget · amount Shield absorbs first, remainder to health.
StatusProceduretarget · status Status application.

The engine has its procedures fixed in code, as a class has its parts. Its one decision is handing each request to the procedure that claims its shape; every other decision is made before submission, by a mutator, or during resolution, by a procedure. A new happening enters as one new procedure and its request; nothing existing changes.

Every decision lives in a procedure; a primitive never decides. A procedure may hold much law, little, or none. The WriteAuthority's primitives comprise the stat write and the structural writes — dock (occupy a board cell), undock (vacate it), container insert, container remove, mint — each existing exactly once (exact roster: open 20). Floors and caps (a6) belong to the write's performance and stay the authority's.

A mutator is the only thing that issues requests. Minting a request is the act of asking: one ask is one request, one mutation, one provenance — the mutator's identity.

A procedure has two entrances, one body. Asked: a mutator issues the procedure's request; the procedure unpacks it and runs. Applied: a procedure, mid-resolution, runs a lower procedure directly, passing the parameters it computed and the request already in its hand. Both entrances run the same body, produce the same events, stamp the same way.

Application stays inside the one mutation. No request is minted on the applied path; no new ask originates inside a resolution. The applying procedure's request travels down as context, so provenance stays singular: a burn's damage carries the burn mutator, a strike's damage carries the strike mutator, and the damaged event is produced identically on either path.

A procedure applies a procedure only when the applied happening happens. Damage happens inside a connecting strike, so the strike procedure applies the damage procedure. Where only a raw write happens, a procedure uses a WriteAuthority primitive: spawn docks a unit — no board move happens.

Returned events. The WriteAuthority returns the fact events of each write; a procedure returns those together with its own events, stamped from the request in its hand; the doorway returns the mutation's events to the submitter. Events are holstered at the payload scope alone — the payload is the unit of issuance and the scope of its holster.
