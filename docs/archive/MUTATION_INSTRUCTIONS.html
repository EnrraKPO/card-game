The write system: how the game changes its facts. An effect carries a trigger (when), a target resolver (whom), and a payload (what); this document establishes the payload and the machinery every write in the game travels.

§1 The system at a glance

an event fires  →  the cascade gathers the roster  →  the conductor runs each effect  →  each mutator issues  →  the MutationEngine dispatches  →  procedures resolve  →  the WriteAuthority commits  →  events return to the holster  →  the boundary fires them depth-first

One effect firing, end to end:

  1. An event fires. The cascade gathers every eligible effect into the roster (§14) and runs it in order, one effect at a time, each through the EffectConductor.
  2. The conductor resolves the effect's targets, cues the windup, pauses the presenter, and engages every mutator of the effect's payload, handing each a per-recipient plate of facts.
  3. Each mutator reasons over its plate and submits zero or more EngineRequests to the MutationEngine.
  4. The engine hands each request to the procedure that claims its shape. The procedure resolves it into writes committed through the WriteAuthority, issues its presentation cues at commit (§13), and returns the mutation's events. Submission is synchronous.
  5. Events travel back by return into the delivery's holster. The conductor unpauses the presenter at the contact cue — the held cues play — cues the conclusion, and returns. The cascade fires the holster's events at the act boundary, depth-first (§12).

§2 Effects are rules

An effect is a rule of the game. The machinery's effects are the base rules; cards, relics, and upgrades add rules on top. Every effect is the triad trigger = when · targets = whom · payload = what, and every effect enters the flow by one road: the trigger.

  • The Game entity holds the base rules. It is a GameEntity (§10): it holds the machinery's effects, and it bears the game's stats — the numbers the base rules consume (mana refill, draws per turn). A rule that tunes the game writes those stats through the road as any stat mutation; conditions interrogate the Game as a source as any other (§17).
  • Every write originates in an effect's payload delivery. Machinery dispatches no payloads. It fires first-mover events — the turn clock, the player's granted ask (§15) — and its effects react.
  • The audience is everything that exists. The cascade polls every effect holder in the world — deck, hand, and graveyard units included. Every effect of a unit carries the implied default condition the holder is fielded on the board, which an authored form may explicitly remove; a non-fielded unit's effects fire only when it does. The condition binds units; holders that are not units are untouched by it. (The removal's authored syntax is out of frame — §19.)

§3 The payload

The payload is a bare typed list on the effect — a bundle of mutators delivered together:

var payload: Array[Mutator]

There is no payload wrapper type: parse validation belongs to the effect's parser, delivery belongs to the conductor, and the list itself has no behavior. One delivery of a payload is the unit of issuance and the scope of the holster (§12).

The authored form is a "payload" array on the effect. Each entry names one mutator: a string where the mutator takes no authored parameters ("strike"), an object naming the mutator with its typed parameters where it does ({"stat_mutation": {"stat": "speed", "delta": 3}}). The parser refuses strangers.

§4 The mutator

A mutator turns an intent — authored by content or constructed by machinery — into concrete requests, using the facts of the firing. A mutator is the only thing that issues requests. One ask is one request, one mutation, one provenance — the mutator's identity kind.

  • Internals are unbounded code. A mutator may read anything and reason however it likes before speaking. The strike mutator asks that the recipient be struck; the draw mutator reads the deck's top from the world and asks that the card move to hand. Markup stays flat, and a new capability is a new mutator in code, never new authoring vocabulary.
  • Contract: issue(plate) → events. Invoked by the conductor; submits zero, one, or several requests and returns the events those mutations produced.
  • Mutator-to-procedure is many-to-few. Differently-reasoning mutators may all conclude in the same request type.
  • The roster is the game's: a mutator exists for each way the game asks for change. Content names an effect's payload mutators; machinery's effects carry mutators constructed in code.
  • Lifecycle: stateless immutable instances. A mutator is constructed once — at parse for an authored effect, in code for a machinery effect — and holds only its authored parameters, never accumulating state across firings; every situational fact arrives on the plate. One instance is therefore shared safely across card copies and simulated worlds. Anything that needs memory is a world fact.
AMENDED (Enrra, 2026-08-18) — Open 30. Every mutator carries a kind: a string identifier (StringName), its name in the roster (§20, Open 23) — "strike", "draw", "pay". An authored mutator's kind is its authored name (§3); machinery-only mutators are named the same way, their names just never appear in markup. The kind is the provenance: everything that carries provenance carries this string, and the mutator object itself never travels.

§5 The plate

Because mutator internals are unbounded, mutator inputs cannot be enumerated. Instead, every mutator receives the same plate of facts at issuance — one uniform signature that never grows. In code the class is Plate, and its facts are four:

  • The world — every question about game state is answerable through it, which is what lets the plate stay closed.
  • The holder — who holds the firing effect.
  • The occasion — the event that fired the effect.
  • The recipient — whom this delivery lands on.

The last three are situational — the circumstances of this issuance, which the world cannot supply. A slot is null where the party does not exist.

§6 The EngineRequest

What a mutator issues, and what the engine receives. The facts changing is the mutation; this object is the asking — minting a request is the act of asking, and only mutators mint. It is a dumb data record: a base class carrying the context bundle common to every request, and one subclass per procedure, named by the happening it asks for, carrying that procedure's parameters as typed members.

class_name EngineRequest          # the base: the context bundle
    var mutator: Mutator          # who asked — identity IS the provenance
    var mutator_kind: StringName  # the manner of the asking — the kind IS the provenance
    var source: GameEntity        # the holder it came from (§10)
    var target: GameEntity        # whom it addresses; null = no target entity exists

class StatMutationRequest extends EngineRequest:
    var stat: StringName
    var delta: int

class StrikeRequest extends EngineRequest:
    pass                          # the striker is the source; the strike procedure
                                  #   reads its attack (§7)

class DamageRequest extends EngineRequest:
    var amount: int
  • The subclass type is the verb. No kind field, no parameter dictionary, no schema shared across verbs.
  • The parameter contract has two parties: the mutators that speak the verb fill the members; the procedure that claims it reads them. The engine transports without reading; conditions interrogate only the context bundle.
  • A request is complete at construction. Context is stamped at issuance and travels unmodified; a null context slot states that the party genuinely does not exist — never "unknown."
  • The context bundle is a floor. A request may carry more than the three slots; the extension mechanism is future work (§19).
AMENDED (Enrra, 2026-08-18) — Open 30. The bundle carries the mutator's kind, not the mutator: the slot is mutator_kind: StringName. No mutator object travels in any request or event.

§7 The MutationEngine and its procedures

The MutationEngine is the single entry point for every mutation in the game. The doorway is MutationEngine.submit(request) — static; synchronous, returning the mutation's events. Requests are self-sufficient, so one doorway serves the live fight and every simulated world. The doorway refuses loudly: a request no procedure claims, or a null target where the verb requires one, is an error at submission — never a silent drop — with the type system closing what it can before runtime. Only mutators mint requests, and only the conductor engages mutators, so no submitter exists outside an open delivery.

A procedure is the game's way of resolving one kind of happening into writes and events. A procedure is a fixed part of the engine, stateless — all state lives in the world's facts — and owns one request shape. Its signature is its typed parameters plus the originating request as context; its events are stamped from that context. In code, the base class is EngineProcedure; each concrete procedure is named by the happening it resolves, and its request pairs with it by that name.

  • The engine has its procedures fixed in code, as a class has its parts. Its one decision is handing each request to the procedure that claims its shape; every other decision is made before submission, by a mutator, or during resolution, by a procedure. A new happening enters as one new procedure and its request; nothing existing changes.
  • A procedure has two entrances, one body. Asked: a mutator issues the procedure's request; the procedure unpacks it and runs. Applied: a procedure, mid-resolution, runs another procedure directly, passing the parameters it computed and the request already in its hand. Both entrances run the same body, produce the same events, stamp the same way.
  • Application stays inside the one mutation. No request is minted on the applied path. The applying procedure's request travels down as context, so provenance stays singular: a burn's damage carries the burn mutator kind, a strike's damage carries the strike mutator kind, and the damaged event is produced identically on either path.
  • A procedure applies a procedure only when the applied happening happens. Damage happens inside a connecting strike, so the strike procedure applies the damage procedure. Where only a raw write happens, a procedure uses a WriteAuthority primitive (§8): spawn docks a unit — no board move happens.
  • Every decision lives in a procedure; a primitive never decides. A procedure may hold much law, little, or none.
ProcedureRequest shapeResolution
StatMutationProceduretarget · stat · delta Applies the delta. Serves stat changes, mana refill, exhaustion.
StrikeProceduretarget (striker = the source) Dodge, crit, amount read from the striker's attack; a connecting strike applies damage.
DamageProceduretarget · amount Shield absorbs first, remainder to health.
StatusProceduretarget · status Mints the status object and inserts it into the target's contained (§9).

The roster covers every write the game performs today; a happening it does not yet speak enters by the rule above — one new procedure and its request.

§8 The WriteAuthority

Every change to a game fact goes through the WriteAuthority. No bypass, from any origin. It performs writes and decides nothing. It is static, matching the engine: requests are self-sufficient and all state lives in the world's facts, so one authority serves the live fight and every simulated world.

  • Its primitives are exactly six — the stat write, dock (occupy a board cell), undock (vacate it), container insert, container remove, and mint — each existing exactly once. The six are an ontology of world structure — a number (the stat write), a board occupancy (dock, undock), a membership (insert, remove), an existence (mint). The roster grows only when a procedure needs a decision-free write no primitive covers; per-container law stays above the primitives, in procedures. Primitive signatures are pinned when procedures are written against them.
  • It owns each fact's arithmetic — floors, caps, whatever governs a specific fact's committed value — in exactly one place. Arithmetic bounds the write's performance; it is not a decision.
  • It returns the fact events of a write. A fact event exists only where content cares — none is issued ahead of need, and any fact mutation, crossing or plain change, bears one the moment something cares about it. Where one exists, the authority detects and returns it — health reaching zero is died — as bare, context-free facts. One author per fact event, blind to which procedure drove the write, so every procedure present or future produces them correctly by construction.
  • The authority is the hardening point. Emerging consequences of facts are written into it with relative freedom; it is monolithic at this scope, and its internal structure is deferred until its contents demand one.

§9 Containers and housing

A container is identity plus members, nothing more: a Container class carrying its owner, its name, and its members — an array of GameEntities. It has no behavior: per-container law lives in procedures (§7), and membership changes ride the insert and remove primitives (§8).

  • Every GameEntity bears one generic container: contained. It enforces nothing about its contents; purpose lives in the contents' own type and rules. A unit's statuses ride its contained like any nested entity; a reader wanting one kind of child filters by checked downcast (§10).
  • Side alone declares named containers — deck, hand, graveyard. Zones are distinct rules, not kinds of contents: the same entity may sit in any of the three, so no type filter could tell them apart. No other named container exists.
  • Finding is navigation. A container is reached as a member of a world object the party already holds — side.deck, entity.contained. No per-entity address lookup exists.
  • One housing per entity. An entity is docked at a coordinate or a member of exactly one container (or newly minted and not yet housed). A container move is remove-from-housing, insert-at-destination; the source is the entity's housing, never searched for.
  • The request carries the container reference; events name the container by its identity.

§10 The entity hierarchy

GameEntity is the common base class for everything that holds effects — and the root of the hierarchy. Holding effects, bearing stats, owning contained, querying, being queued for resolution, and riding in a request's source slot are type-agnostic: the plumbing traffics in GameEntity. Concrete types reappear only where a concrete capacity is exercised — a condition interrogating the source (§17), a procedure reaching its target's concrete capacity (§7), a reader filtering contained (§9) — via checked downcast.

  • The root couples effects, stats, and containment. Every GameEntity holds effects, bears stats, and owns contained. The Game, the sides, the run's holders — relics and upgrades — and statuses are GameEntities directly: the Game's stats are the base rules' numbers (§2); mana lives on the side as a stat; a status's stacks and ticks are stats on the status object. A side holds effects — dormant capacity for side-wide play.
  • BoardEntity derives from the root and adds board presence — a dockable coordinate. Units and board slots are BoardEntities; slots hold effects and statuses — dormant capacity for future boards whose slots take part in play. A card in hand is its unit, the same BoardEntity not yet docked — board presence is the capacity for a coordinate, not the occupancy of one.
  • Everything is typed. The house law: no Variant members, no inferred Variant.
  • Cost, accepted: the base's permanent claim on the hierarchy root — every future holder kind descends from it.

§11 The EffectConductor

The owner of what running one effect means. The triad's parts each answer one question — when, whom, what — and hold no flow; the conductor asks them in order and tells presentation between the steps. It is built by the cascade from the cascade's own (world, presenter) pair, at construction.

The run, exactly:

  1. Resolve the effect's targets against the world. An empty resolution ends the run; it is a legal no-target.
  2. Cue the windup (the effect's windup presentation name, the recipients).
  3. Pause the presenter (§13). Deliver, per-mutator-then-per-recipient: the payload list is the authored sequence, so its order dominates — each mutator speaks its full ask across all recipients before the next mutator begins. Requests flow to the engine as they are issued.
  4. Cue the contact (the effect's contact presentation name, the recipients). The presenter unpauses here; the held cues play (§13).
  5. Cue the conclusion (the windup name closes).

Every cue is awaited. The flow proceeds when presentation greenlights it, and any VFX determines the span of its block (§13). Blocking lives here, in the flow layer — never in the engine.

The conductor ends at step 5. After it returns, the cascade fires the payload's holster (§12).

§12 The act and the holster

An act is one payload delivery. Within one act, everything commits as it happens; between acts, the world responds. The resolution was read at the trigger moment and delivers whole. Every delivery lands whole on every resolved recipient, whatever facts earlier deliveries committed. Mid-walk reads see earlier commits — that is what the delivery order (§11) fixes. Burial waits at the boundary.

No event is dispatched at its own commit. Events wait in the holster — the payload's container of pending events — and fire together once the payload's last mutation has resolved. One holster per payload delivery, owned by the cascade: the cascade opens the delivery and creates the holster; after the conductor returns, the cascade fires the holster's events; the holster dies when its last event has fired and its consequences have unfolded. Nothing persists between deliveries.

The holster is a queue. Events fire in the order they arrived, and every link of the return chain appends its events in resolution order. No ordering mechanism exists; reaction order across a payload follows from the authored payload sequence, the target resolution, and each procedure's body.

Firing is depth-first. An event may trigger a fresh effect, which resolves in full — its own payload, its own holster — before the next event of the outer holster fires.

A death event is an ordinary holstered event, fired and reacted to like any other. Death carries one innate consequence the game itself executes: when a death event's reactions have unfolded, the cascade executes the burial — removal from the board.

§13 Presentation: the pause

A procedure issues its cue on the spot, at commit — named visual, recipient, magnitude — fire-and-forget, synchronous, never awaited. The engine never waits; the return chain carries events alone (§16).

  • The cue's destination is the world's presentation outlet. The live world bears the presenter; a simulated world bears a deaf outlet. A procedure reaches the outlet through the world it writes. No global delivery state exists; nested and cross-world deliveries cannot collide, and resolution is synchronous (§7), so a paused span is never interleaved within its world.
  • The conductor pauses the presenter before engaging the payload and unpauses at the contact cue (§11). Between the last mutation and the unpause, the presenter holds the full cue set and reshapes it at will — merging, sequencing, pacing: its standing authority.
  • Reception is unconditional; playback is gated. A cue arriving while the presenter is paused or mid-cue queues, in arrival order. This queue does not exist in today's code — pacing today is the caller's await chain — and enters with this build.
  • Any VFX determines the span of its block before greenlighting the flow.

§14 The gather and the roster

The gather is a named step of the cascade: an event fires, the cascade gathers every eligible effect into the roster, orders it, and runs it — reactions resolve in roster order. Eligibility is existence: a holder is polled while it exists in the world (§2); the gather inspects no other fact of it — any finer gating is a condition.

Ordering is a two-tier lexicographic comparator, in one place, at the gather: a holder's bucket decides first, the bucket's key decides within. The buckets and their keys:

  1. Relics — acquisition order.
  2. Cards in hand — hand position.
  3. Fielded units and their statuses — turn order; a status resolves immediately after its holding unit.
  4. Board slots — slot order.
  5. Upgrades — acquisition order.
  6. Graveyard units — order of death.

The table grows by amendment — a new holder kind is a new bucket at a weight, finer granularity is a refined key — and the mechanism never restructures.

§15 Activation

Every activatable holder — a card to play, an ability to use, a consumable to spend — bears an activation effect:

  • Trigger: activation_invoked — the first-mover event a player's or the AI's ask fires, addressed to it.
  • Conditions: payability — cost within open mana, tap unspent — the machinery's clause, written once, referenced by every activation effect; plus whatever gating its content authors. An ask that fails the conditions is a lawful non-reaction: nothing pays, nothing unfolds.
  • Payload: the pay mutator, alone.

The PayCostProcedure claims the pay request, commits the cost through the WriteAuthority, and returns its procedure event cost_paid, whose context carries who paid and for what. The substantive content — the card's played doing, the ability's payload — triggers on cost_paid with the payment-is-mine condition (§17) and resolves depth-first at the payment act's boundary.

Playability is queried, never re-spelled. Presentation and the AI ask an activation effect's conditions read-only — "would this pass now" — and offer only what passes. The payability clause has one author; no consumer restates it.

§16 Events

An event born of a request has two halves:

  • The carried half — the request's context bundle (mutator mutator kind, source, target), forwarded with every event the request gives rise to. Provenance is the mutator's identity kind; there is no separate provenance vocabulary.
  • The produced half — what actually happened at commit: died, shield emptied, health lost. Fact events are authored by the WriteAuthority; procedure events (struck, dodged, cost_paid) are authored by the resolving procedure. "Died from poison" reads both halves.

Events travel by return. The WriteAuthority returns the fact events of each write; a procedure returns those together with its own events, stamped from the request in its hand; the doorway returns the mutation's events to the submitter; the mutator returns them from issue(); the conductor collects them into the delivery's holster. Events are holstered at the payload scope alone.

Effect boundaries restart the context. When an event triggers another effect, that effect's requests carry their own context; context never accumulates across effects.

First-mover events share the one event shape. Events born of no request — the turn's start and end, a unit's turn coming due, activation_invoked — are fired by machinery and carry the same context bundle with its slots honestly null; there is no second event vocabulary.

Event names are past-tense happening verbs — died, struck, dodged, crit, damaged, cost_paid — settled fact-by-fact and procedure-by-procedure. A name enters the roster only when content needs its event (§8): moved, spawned, buried, and drawn arrive as their procedures build and content asks.

§17 Conditions interrogate the source

The source slot carries the actual holder object, and trigger conditions are predicates asked of it. "Was the death caused by me" is an identity comparison; "was the source a fire unit" is a checked downcast plus a property read. A failed downcast is a clean false: a relic-sourced death is not "caused by a fire unit." A real object answers any predicate written against it, present or future, with nothing added to the request's shape.

§18 Genesis is construction, not mutation

The world is constructed whole: setup builds every entity in its starting container directly, before the first event fires. The write road governs play — every change from the first first-mover event onward. The mint primitive and the SpawnProcedure serve existence that begins mid-play.

§19 Out of frame

Named so absence is never read as oversight:

  • Interception.
  • The context-bundle extension mechanism (§6).
  • The procedures' internal arithmetic — dodge odds, crit numbers — each arrives by its own instructions; §7 fixes where they live (the strike procedure), not what they compute.
  • The authored syntax that removes the implied fielded condition (§2) — the payload markup (§3) does not carry it.
  • The procedures' build order.
  • Status removal — expiry and cleanse. Its committed write is a container remove (§8); its procedure enters with the first content that removes a status.

  4. Open 26 — strike arithmetic at build one. §19 defers dodge and crit numbers to their own instructions, yet §7 obliges StrikeProcedure to resolve dodge and crit. To rule: carry the existing arithmetic over as-is, or the procedure enters without dodge and crit until their instructions arrive.
    RULED (Enrra, 2026-08-17; seeds and the difference term 2026-08-18). Strike enters with dodge and crit at build one. The mechanics are stated here in full; this ruling supersedes CRIT_DAMAGE_SPEC.md, retired to record.

    The chance formula, shared by both mechanics:
    chance = base + own Speed × speed rating + difference rating × max(0, Speed difference), capped. The difference term is one-sided: only a positive difference contributes. Dodge rolls from the defender (difference = defender minus attacker); crit rolls from the attacker (difference = attacker minus defender).

    Dodge rolls first. A dodge ends the strike — no damage, no crit — and produces the dodged event. Buildings never dodge.

    Crit rolls only on a connecting strike whose damage, after mitigation, is above zero. On success the damage is multiplied by the crit multiplier (flat, capped) and the crit event is produced. Buildings crit and are crit normally.

    The pipeline, fixed: dodge → (interception — out of frame, slot reserved) → crit → damage.

    The numbers are stats of the Game entity — per mechanic: base, speed rating, difference rating, cap; plus the crit multiplier and its cap. Seeded from data at construction, mutable through the road like any stat. The seeds: dodge — 0% base, 1% per Speed, 4% per difference point, 75% cap; crit — 5% base, 1% per Speed, 0% per difference point, 75% cap, multiplier ×2.0, multiplier cap ×5.0.

  5. Open 27 — the payability clause's home. §15 declares it written once and referenced by every activation effect; where it lives is unstated.
    RULED (Enrra, 2026-08-17; the noun and the ordinary-condition nuance 2026-08-18). The effect that answers an activation is the pay effect — named by its one mutation, paying; "activation" names its trigger (activation_invoked). Payability is a trigger condition of the pay effect, and the pay effect is an ordinary effect: an unaffordable ask fails its conditions and nothing triggers. The machinery bakes one affordability condition onto every pay effect — an ordinary condition in every respect, shared by all cards and baked to spare authoring it each time; authored content may overrule it as it may any condition. Consumers never read an effect's conditions — the established main-action pattern governs the query: the unit exposes one query method — is this ability payable — and its pay effect, the appointed holder of the slot, answers from its own conditions. §15's "activatable holder" and "activation effect" language are amendment targets.
  6. Open 28 — one road to presentation, said two ways. §11 builds the conductor from the cascade's (world, presenter) pair; §13 reaches presentation through the world's outlet. One statement should govern both.
    VOID (2026-08-17): the ruling below was recorded without being pronounced — Enrra stated the problem (two worlds, different presentation layers or none), never the mechanism. Scratched; Open 28 remains open.

    The authority: presentation is the final authority on what is allowed to proceed. A playing cue owns the flow, totally, for as long as it wants; anything arriving meanwhile queues behind it. A paused presenter is playing nothing and therefore owns nothing — the machinery runs free through a delivery not by exemption but because the authority is, at that moment, exercised on nothing.

    The road: presentation is reached through the world, because presentation identity is a fact of the world — the live world bears the presenter, a simulated world bears none. Every speaker, conductor and procedure alike, fetches it from the world it works in; no component is handed a presenter alongside the world, and rule code never asks which world it is in. §11's (world, presenter) pair is an amendment target.

    RULED (Enrra, 2026-08-18) — Open 28 closed. Presentation is reached through the world, everywhere. The world owns its presentation outlet: the live world's outlet is the presenter; a simulated world's outlet is deaf (§13).
