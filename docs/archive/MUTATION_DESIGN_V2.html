The Mutation of Facts II

Retired to record — superseded by MUTATION_INSTRUCTIONS.html (2026-08-17) Drafted: 2026-08-16 Branch: nuke-channel Supersedes: MUTATION_DESIGN.html (retired to record)

The write system: how the game changes its facts. An effect carries a trigger (when) and a target resolver (whom); this pitch document establishes the third slot (what) — and the machinery every write in the game travels, effect-borne and machinery- borne alike.

§1 The system at a glance

a payload delivers  →  each mutator issues  →  the MutationEngine dispatches  →  procedures resolve  →  the WriteAuthority commits  →  events return to the issuer  →  the payload's holster gathers them  →  the cascade fires the holster

One effect firing, end to end:

  1. The cascade catches a trigger (or the activation entrance is invoked) and hands the effect to its EffectConductor.
  2. The conductor resolves the effect's targets, cues the windup, and engages every mutator of the effect's payload, handing each a per-recipient plate of facts.
  3. Each mutator reasons freely over its plate and submits zero or more EngineRequests to the MutationEngine.
  4. The engine hands each request to the procedure that claims its shape; the procedure resolves it — applying other procedures where their happenings happen — into writes committed through the WriteAuthority. Submission is synchronous and returns the mutation's events, which the conductor collects for the delivery's holster (§9).
  5. The conductor cues the contact and the conclusion. The cascade then fires the payload's holster (§9).

The audience: the cascade polls every effect holder that exists in its world — fielded units and slots, their statuses, the sides, the run's holders (relics, upgrades), and cards in hand — deck, hand, and graveyard units included (§14, ruling of Open 19). Every effect carries an implied default condition — the holder is not a unit sitting in hand the holder, if a unit, is fielded on the board — which an authored form may explicitly remove; a hand-held non-fielded card's effects fire only when it does. (The removal's authored syntax is out of frame — §13.)

§2 The payload

The effect's anatomy is a triad: trigger = when · targets = whom · payload = what. The payload is a bare typed list on the effect — a bundle of mutators delivered together:

var payload: Array[Mutator]

There is no payload wrapper type: parse validation belongs to the effect's parser, delivery belongs to the conductor, and the list itself has no behavior. One delivery of a payload is the unit of issuance and the scope of the holster (§9). An effect bears its payload; machinery hands the cascade a bare list on the spot. Machinery's asks are borne by machinery-held effects — the game's base rules, held by the Game entity (§14, ruling of Open 17).

The authored form is a "payload" array on the effect. Each entry names one mutator: a string where the mutator takes no authored parameters ("strike"), an object naming the mutator with its typed parameters where it does ({"stat_mutation": {"stat": "speed", "delta": 3}}). The parser refuses strangers.

§3 The mutator

A mutator is the game's asking voice: a content-nameable object that turns an intent — authored by content or constructed by machinery — into concrete requests, using the facts of the firing. A mutator is the only thing that issues requests. One ask is one request, one mutation, one provenance — the mutator's identity.

  • Internals are unbounded code. A mutator may read anything and reason however it likes before speaking. The strike mutator asks that the recipient be struck; the draw mutator reads the deck's top from the world and asks that the card move to hand. Markup stays flat, and a new capability is a new mutator in code, never new authoring vocabulary.
  • Contract: issue(plate) → events. Invoked by the conductor; submits zero, one, or several requests and returns the events those mutations produced.
  • Mutator-to-procedure is many-to-few. Differently-reasoning mutators may all conclude in the same request type.
  • The roster is the game's: a mutator exists for each way the game asks for change. Content names an effect's payload mutators; machinery constructs its own in code.
  • Lifecycle: stateless immutable instances. A mutator is constructed once — at parse for an authored effect, on the spot by machinery — and holds only its authored parameters, never accumulating state across firings; every situational fact arrives on the plate. One instance is therefore shared safely across card copies and simulated worlds. Provenance identifies the ask as authored; the request's source slot answers whose. Anything that needs memory is a world fact.

§4 The plate

Because mutator internals are unbounded, mutator inputs cannot be enumerated. Instead, every mutator receives the same plate of facts at issuance — one uniform signature that never grows. In code the class is Plate, and its facts are four:

  • The world — every question about game state is answerable through it, which is what lets the plate stay closed.
  • The holder — who holds the firing effect.
  • The occasion — the event that fired the effect.
  • The recipient — whom this delivery lands on.

The last three are situational — the circumstances of this issuance, which the world cannot supply. Machinery issuing outside any effect's firing fills the same four slots, null where the party does not exist.

§5 The EngineRequest

What a mutator issues, and what the engine receives. The facts changing is the mutation; this object is the asking — minting a request is the act of asking, and only mutators mint. It is a dumb data record: a base class carrying the context bundle common to every request, and one subclass per procedure, named by the happening it asks for, carrying that procedure's parameters as typed members.

class_name EngineRequest          # the base: the context bundle
    var mutator: Mutator          # who asked — identity IS the provenance
    var source: GameEntity        # the holder it came from (§11)
    var target: GameEntity        # whom it addresses; null = no target entity exists

class StatMutationRequest extends EngineRequest:
    var stat: StringName
    var delta: int

class StrikeRequest extends EngineRequest:
    pass                          # the striker is the source; the strike procedure
                                  #   reads its attack (§6)

class DamageRequest extends EngineRequest:
    var amount: int
  • The subclass type is the verb. No kind field, no parameter dictionary, no schema shared across verbs.
  • The parameter contract has two parties: the mutators that speak the verb fill the members; the procedure that claims it reads them. The engine transports without reading; conditions interrogate only the context bundle.
  • A request is complete at construction. Context is stamped at issuance and travels unmodified; a null context slot states that the party genuinely does not exist — never "unknown."
  • The context bundle is a floor. A request may carry more than the three slots; the extension mechanism is future work (§13).

§6 The MutationEngine and its procedures

The MutationEngine is the single entry point for every mutation in the game. The doorway is MutationEngine.submit(request) — static, callable from anywhere; synchronous, returning the mutation's events. Requests are self-sufficient, so one doorway serves the live fight and every simulated world. The doorway refuses loudly: a request no procedure claims, or a null target where the verb requires one, is an error at submission — never a silent drop — with the type system closing what it can before runtime.

A procedure is the game's way of resolving one kind of happening into writes and events. A procedure is a fixed part of the engine, stateless — all state lives in the world's facts — and owns one request shape. Its signature is its typed parameters plus the originating request as context; its events are stamped from that context. In code, the base class is EngineProcedure; each concrete procedure is named by the happening it resolves, and its request pairs with it by that name.

  • The engine has its procedures fixed in code, as a class has its parts. Its one decision is handing each request to the procedure that claims its shape; every other decision is made before submission, by a mutator, or during resolution, by a procedure. A new happening enters as one new procedure and its request; nothing existing changes.
  • A procedure has two entrances, one body. Asked: a mutator issues the procedure's request; the procedure unpacks it and runs. Applied: a procedure, mid-resolution, runs another procedure directly, passing the parameters it computed and the request already in its hand. Both entrances run the same body, produce the same events, stamp the same way.
  • Application stays inside the one mutation. No request is minted on the applied path; no new ask originates inside a resolution. The applying procedure's request travels down as context, so provenance stays singular: a burn's damage carries the burn mutator, a strike's damage carries the strike mutator, and the damaged event is produced identically on either path.
  • A procedure applies a procedure only when the applied happening happens. Damage happens inside a connecting strike, so the strike procedure applies the damage procedure. Where only a raw write happens, a procedure uses a WriteAuthority primitive (§7): spawn docks a unit — no board move happens.
  • Every decision lives in a procedure; a primitive never decides. A procedure may hold much law, little, or none.
ProcedureRequest shapeResolution
StatMutationProceduretarget · stat · delta Applies the delta. Serves stat changes, mana pay and refill, exhaustion.
StrikeProceduretarget (striker = the source) Dodge, crit, amount read from the striker's attack; a connecting strike applies damage.
DamageProceduretarget · amount Shield absorbs first, remainder to health.
StatusProceduretarget · status Mints the status object and inserts it into the target's statuses container contained (§14, Open 21).
ContainerMoveProceduretarget · a side's coordinate-less container (deck, hand, graveyard) Draw, burial, discard.
BoardMoveProceduretarget · BoardLocation Placement and movement on the board.
SpawnProcedurecard id · BoardLocation Mints a unit into existence on the board.

The roster covers every write the game performs today; a happening it does not yet speak enters by the rule above — one new procedure and its request.

§7 The WriteAuthority

Every change to a game fact goes through the WriteAuthority. No bypass, from any origin. It performs writes and decides nothing. It is static, matching the engine: requests are self-sufficient and all state lives in the world's facts, so one authority serves the live fight and every simulated world.

  • Its primitives are exactly six — the stat write, dock (occupy a board cell), undock (vacate it), container insert, container remove, and mint — each existing exactly once. A container is any coordinate-less collection of world objects: a side's deck, hand, and graveyard, and a BoardEntity's statuses alike and every GameEntity's contained (§14, ruling of Open 21). The six are an ontology of world structure — a number (the stat write), a board occupancy (dock, undock), a membership (insert, remove), an existence (mint). The roster grows only when a procedure needs a decision-free write no primitive covers; per-container law stays above the primitives, in procedures. Primitive signatures are pinned when procedures are written against them.
  • It owns each fact's arithmetic — floors, caps, whatever governs a specific fact's committed value — in exactly one place. Arithmetic bounds the write's performance; it is not a decision.
  • It returns the fact events of a write. A fact event exists only where content cares — none is issued ahead of need, and any fact mutation, crossing or plain change, bears one the moment something cares about it. Where one exists, the authority detects and returns it — health reaching zero is died — as bare, context-free facts. One author per fact event, blind to which procedure drove the write, so every procedure present or future produces them correctly by construction.
  • The authority is the hardening point. Emerging consequences of facts are written into it with relative freedom; it is monolithic at this scope, and its internal structure is deferred until its contents demand one.

§8 The EffectConductor

The owner of what running one effect means. The triad's parts each answer one question — when, whom, what — and hold no flow; the conductor asks them in order and tells presentation between the steps. It is built by the cascade from the cascade's own (world, presenter) pair, at construction.

The run, exactly:

  1. Resolve the effect's targets against the world. An empty resolution ends the run; it is a legal no-target.
  2. Cue the windup (the effect's windup presentation name, the recipients).
  3. Deliver, per-mutator-then-per-recipient: the payload list is the authored sequence, so its order dominates — each mutator speaks its full ask across all recipients before the next mutator begins. Requests flow to the engine as they are issued. The presenter is paused for the span of this step (§14, ruling of Open 20).
  4. Cue the contact (the effect's contact presentation name, the recipients). The presenter runs the act's account here (§9). The presenter unpauses here; the held cues play (§9, as ruled in §14 / Open 20).
  5. Cue the conclusion (the windup name closes).

Every cue is awaited. The flow proceeds when presentation greenlights it, and any VFX determines the span of its block (§9). Blocking lives here, in the flow layer — never in the engine.

The conductor ends at step 5. After it returns, the cascade fires the payload's holster (§9).

Two entrances, one conductor: triggered dispatch enters through the cascade's event machinery; the activation path (effects with a cost instead of a trigger — abilities, consumables) enters through a cascade entrance that skips audience-and-trigger and invokes the same conductor. Effects enter the flow by one road: the trigger. Activation is ruled in §14 (Open 17).

§9 The act, the holster, and the account

An act is one payload delivery. Within one act, everything commits as it happens; between acts, the world responds. The resolution was read at the trigger moment and delivers whole. Facts change instantly mid-act — a killed unit is dead that instant — but reactions open at the act boundary: three units killed by one blow died simultaneously, whatever order their requests committed in.

The commit sequence inside an act is mechanical bookkeeping, not game-time. No recipient is ever "already dead" for delivery purposes: every delivery lands whole on every resolved recipient, and a unit becomes a corpse as the act resolves, by the act's totality. Every delivery lands whole on every resolved recipient, whatever facts earlier deliveries committed. Mid-walk reads do see earlier commits — that is what the delivery order (§8) fixes — but no decision about delivery hangs on the sequence. Burial waits at the boundary.

The mutations of one payload are simultaneous for the purpose of event firing. No event is dispatched at its own commit. Events wait in the holster — the payload's container of pending events — and fire together once the payload's last mutation has resolved. One holster per payload delivery, owned by the cascade: the cascade opens the delivery and creates the holster; after the conductor returns, the cascade fires the holster's events in order; the holster dies when its last event has fired and its consequences have unfolded. Nothing persists between deliveries.

Firing is depth-first. An event may trigger a fresh effect, which resolves in full — its own payload, its own holster — before the next event of the outer holster fires.

A death event is an ordinary holstered event, fired and reacted to like any other. Death carries one innate consequence the game itself executes: when a death event's reactions have unfolded, the cascade executes the burial — removal from the board.

Announcements are gathered, not performed. Beside the holster, the act has a second gathered output: the act's account. A procedure announcing at commit records what happened — named visual, recipient, magnitude — into the account. The cascade opens the account beside the holster, and both belong to the delivery; while the delivery is open, the account is reachable statically, so a procedure announces into it directly — no reference threads through the engine, and the return chain carries events alone (§10). Nothing plays mid-resolution, and the engine never waits. At the contact cue (§8), the presenter receives the whole account and runs it at its own will — merging, sequencing, and pacing its cues with full authority — and any VFX determines the span of its block before greenlighting the flow. A simulated world runs the same road with no presenter attached: its account plays nothing. Presentation transport is the presenter's pause (§14, ruling of Open 20). A procedure issues its cue at commit, fire-and-forget, to the world's presentation outlet — the live world bears the presenter, a simulated world a deaf outlet. The conductor pauses the presenter before engaging the payload and unpauses at the contact cue; the presenter reshapes the held set at will before playing. A cue arriving while the presenter is paused or mid-cue queues, in arrival order. The return chain carries events alone (§10); the engine never waits.

§10 Events

An event born of a request has two halves:

  • The carried half — the request's context bundle (mutator, source, target), forwarded with every event the request gives rise to. Provenance is the mutator's identity; there is no separate provenance vocabulary.
  • The produced half — what actually happened at commit: died, shield emptied, health lost. Fact events are authored by the WriteAuthority; procedure events (struck, dodged) are authored by the resolving procedure. "Died from poison" reads both halves.

Events travel by return. The WriteAuthority returns the fact events of each write; a procedure returns those together with its own events, stamped from the request in its hand; the doorway returns the mutation's events to the submitter; the mutator returns them from issue(); the conductor collects them into the delivery's holster. Events are holstered at the payload scope alone.

Effect boundaries restart the context. When an event triggers another effect, that effect's requests carry their own context; context never accumulates across effects.

Events born of no request share the one event shape. Phase markers — the turn's start and end, a unit's turn coming due — carry the same context bundle with its slots honestly null; there is no second event vocabulary.

Event names are past-tense happening verbs — died, struck, dodged, crit, damaged — settled fact-by-fact and procedure-by-procedure. A name enters the roster only when content needs its event (§7): moved, spawned, buried, and drawn arrive as their procedures build and content asks.

§11 The entity hierarchy

GameEntity is the common base class for everything that holds effects — and the root of the hierarchy. Holding effects, bearing stats, querying, being queued for resolution, and riding in a request's source slot are type-agnostic: the plumbing traffics in GameEntity. Concrete types reappear only where a concrete capacity is exercised — a condition interrogating the source (§12), a procedure reaching its target's concrete capacity (§6) — via checked downcast.

  • The root couples effects and stats. Every GameEntity holds effects and bears stats. The run's holders — relics and upgrades — and statuses are GameEntities directly; a status's stacks and ticks are stats on the status object. A side is a GameEntity too: mana lives on the side as a stat (§6), and a side holds effects — dormant capacity for side-wide play.
  • BoardEntity derives from the root and adds board presence — a dockable coordinate — and with it the statuses container: holding statuses couples to board presence. A unit's statuses ride its contained like any nested entity (§14, ruling of Open 21). Units and board slots are BoardEntities; slots thereby hold effects and statuses — dormant capacity for future boards whose slots take part in play. A card in hand is its unit, the same BoardEntity not yet docked — board presence is the capacity for a coordinate, not the occupancy of one — which is how the audience (§1) reaches a hand-held card's effects.
  • Everything is typed. The house law: no Variant members, no inferred Variant.
  • Cost, accepted: the base's permanent claim on the hierarchy root — every future holder kind descends from it.

§12 Conditions interrogate the source

The source slot carries the actual holder object, and trigger conditions are predicates asked of it. "Was the death caused by me" is an identity comparison; "was the source a fire unit" is a checked downcast plus a property read. A failed downcast is a clean false: a relic-sourced death is not "caused by a fire unit." A real object answers any predicate written against it, present or future, with nothing added to the request's shape.

§13 Out of frame

Named so absence is never read as oversight:

  • Interception.
  • The context-bundle extension mechanism (§5).
  • The procedures' internal arithmetic — dodge odds, crit numbers — each arrives by its own pitch instructions; §6 fixes where they live (the strike procedure), not what they compute.
  • The authored syntax that removes the implied hand condition (§1) — the payload markup (§2) does not carry it.
  • The procedures' build order.
  • Status removal — expiry and cleanse. Its committed write is a container remove (§7); its procedure enters with the first content that removes a status.
  • The machinery-borne delivery's conduct — the cascade's entrance for a bare list, and where its account plays. Dissolved — no such delivery exists (§14, ruling of Open 17). The write road itself (§3–§7) is machinery's in full.

§14 Opens of the 2026-08-17 inspection

Raised on inspection before signing; each awaits a ruling.

Open 15Reaction order among multiple reactors. §9 fixes the order of events within a holster, but when one fired event triggers effects on several holders at once — two relics and a unit all reacting to the same died — nothing states in what order those reactions resolve.

Ruling (2026-08-17). The gather is a named step of the cascade: an event fires, the cascade gathers every eligible effect into the roster, orders it, and runs it — reactions resolve in roster order. Ordering is a two-tier lexicographic comparator, in one place, at the gather: a holder's bucket decides first, the bucket's key decides within. The buckets and their keys:

  1. Relics — acquisition order.
  2. Cards in hand — hand position.
  3. Fielded units and their statuses — turn order; a status resolves immediately after its holding unit.
  4. Board slots — slot order.
  5. Upgrades — acquisition order.
  6. Graveyard units — order of death.

A bucket exists for every holder kind the comparator can meet; whether a kind is polled at all is the audience's law (§1), not this table's. The table grows by amendment — a new kind is a new bucket at a weight, finer granularity is a refined key — and the mechanism never restructures.

Open 16Whether the dead may react. A killed unit is dead mid-act but stands unburied while the holster fires (§9). Its own on-death effect must plainly fire — that is why burial waits — but the general rule is unstated: does a dead-but-unburied holder react to other events in the holster?

Void (2026-08-17). The question was manufactured by §9's scratched language — the document defines no mid-act death state to legislate. Eligibility is existence (§1); any finer gating is a condition, and none has been ruled.

Open 17The activation path's cost. §8 routes activated effects (a cost instead of a trigger) through a cascade entrance into the same conductor, but nothing in the document checks or pays the cost, and cost is not in §13. Who verifies affordability, and who mints the paying request?

Ruling (2026-08-17). An effect is a rule of the game. The machinery's effects are the base rules; cards, relics, and upgrades add rules on top. One holder roots the base rules: the Game entity — a GameEntity holding the machinery's effects and bearing the game's stats, the numbers the base rules consume (mana refill, draws per turn). A rule that tunes the game writes those stats through the road as any stat mutation; conditions interrogate the Game as a source like any other (§12).

Every write originates in an effect's payload delivery. Machinery dispatches no payloads. It fires first-mover events — the turn clock, the player's granted ask — as §10's events born of no request, and its effects react. Effects enter the flow by one road: the trigger.

Activation: one gate outside the mutation system reads the world and refuses an unready or unaffordable ask; nothing else validates. A granted ask fires the first-mover event activation_invoked. The Game entity's pay effect triggers on it and delivers the pay mutator; the pay-cost procedure resolves the cost — mana and tap committed through the WriteAuthority — and returns the procedure event cost_paid. The activated effect bears trigger = cost_paid with the condition that the payment is its own (§12). The payment is one act; the activated effect resolves depth-first at its boundary.

Activation (amended 2026-08-17, same session). Every activatable holder — a card to play, an ability to use, a consumable to spend — bears an activation effect: trigger = activation_invoked (the first-mover event a player's or the AI's ask fires, addressed to it); conditions = payability (the machinery's clause — cost within open mana, tap unspent — written once, referenced by every activation effect) plus whatever gating its content authors; payload = the pay mutator, alone. An ask that fails the conditions is a lawful non-reaction: nothing pays, nothing unfolds. The pay-cost procedure claims the pay request, commits the cost through the WriteAuthority, and returns its procedure event cost_paid, whose context carries who paid and for what. The substantive content — the card's played doing, the ability's payload — triggers on cost_paid with the payment-is-mine condition (§12) and resolves depth-first at the payment act's boundary.

Playability is queried, never re-spelled. Presentation and the AI ask an activation effect's conditions read-only — "would this pass now" — and offer only what passes. The payability clause has one author; no consumer restates it.

Scratched under this ruling: §2's bare-list dispatch, §8's activation entrance, §13's machinery-borne-delivery item.

Open 18submit() outside any open delivery. The doorway is callable from anywhere (§6), yet the holster and the account exist only while a delivery is open (§9). A submission with no delivery open has no home for its returned events or its announcements. Either the doorway refuses it, or its conduct is named out of frame — silence is neither.

Ruling (2026-08-17). Closed by construction under the ruling of Open 17: every write originates in an effect's payload delivery, only the conductor engages mutators, and only mutators mint requests — no submitter exists outside an open delivery.

Open 19Card-entity lifecycle. Draw is a ContainerMove of an existing entity (§6), and a hand card is its unit (§11) — so a deck card is already a minted BoardEntity, yet nothing states when or by what authority a player's deck units are minted (SpawnProcedure mints onto the board only). Related: §1's audience list excludes the deck, but "polls every effect holder that exists in its world" now includes deck units, and the implied default condition names only the hand — as written, a deck-sitting unit's effects arguably fire.

Ruling (2026-08-17). Genesis is construction, not mutation. The world is constructed whole: setup builds every entity in its starting container directly, before the first event fires. The write road governs play — every change from the first first-mover event onward. The mint primitive and the SpawnProcedure serve existence that begins mid-play.

The audience is everything that exists. Every effect holder in the world is polled — deck, hand, and graveyard units included. The implied default condition on a unit's effects is the holder is fielded on the board; hand, deck, and graveyard are gated out by that one condition, which authored content may remove (§1). The condition binds units; holders that are not units are untouched by it.

Open 20One delivery at a time? Cues are awaited, so a delivery stays open across async spans, while the account and holster are reachable statically (§9). The single-open-delivery invariant is unstated — as is what happens if a simulated world runs a delivery while the live one sits at an awaited cue.

Ruling (2026-08-17). The account is dissolved — it was never ruled; §9's account paragraph is scratched, and presentation transport is the presenter's pause:

  • A procedure issues its cue on the spot, at commit — fire-and-forget, synchronous, never awaited.
  • The cue's destination is the world's presentation outlet: the live world bears the presenter; a simulated world bears a deaf outlet. A procedure reaches the outlet through the world it writes. No global delivery state exists; nested and cross-world deliveries cannot collide, and resolution is synchronous (§6), so a paused span is never interleaved within its world.
  • The conductor pauses the presenter before engaging the payload and unpauses at the contact cue. Between the last mutation and the unpause, the presenter holds the full cue set and reshapes it at will — merging, sequencing, pacing (its standing authority).
  • Reception is unconditional; playback is gated. A cue arriving while the presenter is paused or mid-cue queues, in arrival order. This queue does not exist in today's code — pacing today is the caller's await chain — and enters with this build.
Open 21The container member's type. ContainerMoveRequest addresses "a side's coordinate-less container" (§6), but no stated type denotes one — what object names "a side's hand" in the typed request?

Ruling (2026-08-17). A container is identity plus members, nothing more: a Container class carrying its owner, its name, and its members — an array of GameEntities. It has no behavior: per-container law lives in procedures (§7), and membership changes ride the insert and remove primitives.

  • Every GameEntity bears one generic container: contained. It enforces nothing about its contents; purpose lives in the contents' own type and rules. A unit's statuses ride its contained like any nested entity; a reader wanting one kind of child filters by checked downcast (§11's standing pattern). There is no statuses container.
  • Side alone declares named containers — deck, hand, graveyard. Zones are distinct rules, not kinds of contents: the same entity may sit in any of the three, so no type filter could tell them apart. No other named container exists.
  • Finding is navigation: a container is reached as a member of a world object the party already holds. No per-entity address lookup exists.
  • One housing per entity: an entity is docked at a coordinate or a member of exactly one container (or newly minted and not yet housed). A container move is remove-from-housing, insert-at-destination; the source is the entity's housing, never searched for.
  • The request carries the container reference; events name the container by its identity.

Scratched under this ruling: §7's "a BoardEntity's statuses" example, §6's StatusProcedure wording, §11's coupling of the statuses container to board presence.

Open 22The holster's firing order. §9 fires the holster's events "in order" without saying which order. Commit order is the natural reading; the contract should say it.

Ruling (2026-08-17). A non-issue: there is nothing to order. The holster is a queue — events fire in the order they arrived, and every link of the return chain appends its events in resolution order. No ordering mechanism exists; reaction order across a payload follows from the authored payload sequence, the target resolution, and each procedure's body.
